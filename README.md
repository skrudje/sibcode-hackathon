# Хрюкерсы CDP

Рабочий MVP кейса №2 SibКод: клиентская платформа торгового центра. Объединяет данные арендаторов, показывает историю посетителя, рассчитывает сегменты и объяснимые рекомендации, готовит аудитории для внешней рассылки.

Репозиторий: https://github.com/skrudje/sibcode-hackathon. Рабочая папка на исходном компьютере — `/data/sibcode`. [Работа втроём](docs/TEAM.md) · [Desktop Linux/Windows](docs/DESKTOP.md).

[Результаты проверки MVP](docs/VERIFICATION.md) · [Скриншот интерфейса](docs/screenshots/overview.png)

## Desktop-разработка

Целевое приложение — Tauri 2 для Linux и Windows. Интерфейс упакован локально и подключается к серверу CDP. Подготовьте зависимости Tauri по [инструкции](docs/DESKTOP.md), запустите backend через Compose, затем из `apps/web` выполните `npm ci` и `npm run desktop:dev`. Для сборки установщика — `npm run desktop:build`. Подробности и границы автономности описаны в `docs/DESKTOP.md`.

## Быстрый запуск

Требуются Docker Engine и Docker Compose (на Windows — Docker Desktop с Linux containers). Все команды ниже выполняются из корня репозитория.

```bash
cp .env.example .env
docker compose up --build -d --wait
```

Если `.env` уже существует и настроен, сохраняйте его вместо повторного копирования.

Открыть **http://localhost:5180**.

Демонстрационная учётная запись из `.env.example`:

- Email: `marketer@example.com`
- Пароль: `HryukersDemo2026!`

Это известные локальные демозначения. Рабочая учётная запись создаётся из `DEMO_EMAIL`/`DEMO_PASSWORD` при первом seed. Изменение переменных после первого запуска не меняет сохранённый пароль пользователя.

Вход защищён серверной сессией. Данные хранятся в PostgreSQL, а не в браузерных моках. Наружу сервисы привязаны к loopback; `WEB_PORT`, `POSTGRES_PORT`, `VALKEY_PORT` можно изменить в env. При смене web-порта обновите `ALLOWED_ORIGINS`.

## Что реализовано

- Tauri 2: desktop-клиент Linux/Windows, настройки сервера, native HTTP-сессия и диалог сохранения CSV.
- React/TypeScript/Vite, Tailwind и локальные UI-компоненты в стиле shadcn, Radix Dialog, TanStack Query.
- FastAPI, Pydantic, PostgreSQL 18, SQLAlchemy, Alembic.
- Закрытый кабинет, cookie-сессии, Argon2, проверка origin и границ ТЦ.
- CRM CSV, касса XLSX, REST JSON: разные адаптеры, единые валидация и сохранение фактов.
- API явного изменения полноты истории источника; ошибки заголовков CSV/XLSX перечисляют отсутствующие и повторяющиеся колонки. [Форматы файлов и API покрытия](docs/IMPORT_FORMATS.md).
- Профили связываются по общему ключу; совпадение контакта не сливает людей. Конфликты и записи без подтверждённого ключа видны отдельно.
- Повтор события не дублирует историю; изменённое содержимое того же ID отклоняется.
- Импорт проходит через Valkey/RQ; задания, lease и результаты строк долговременно хранятся в PostgreSQL. Dispatcher восстанавливает задания после сбоев.
- Сегменты с AND/NOT, окном истории и состоянием unknown. Результат вычисляется по актуальным фактам при запросе.
- Редактируемые рекомендации с действующим предложением, приоритетом и объяснением через реальные события.
- [Радар новых визитов](docs/RADAR.md): поиск наблюдаемых связей арендаторов, карта, проверка аудитории и создание динамического сегмента с кампанией.
- Кампании email/SMS/push, предпросмотр исключений, идемпотентная CSV-выгрузка, cooldown и защита от конкурентных повторов.
- Все страницы используют реальные API. Есть мобильная вёрстка, loading/empty/error состояния и сценарий демонстрации.

## Демонстрация за 5–7 минут

1. Войти и на обзоре нажать **«Запустить демосценарий»**. Браузер последовательно вызывает реальную API-синхронизацию кинотеатра и загрузку XLSX кафе/CSV книжного. События не подгружаются скрытым seed.
2. На странице источников показать журнал: 22 строки, 18 принятых, 1 дубль, 3 отклонённых. Открыть причины ошибок.
3. В клиентах найти **G001** и открыть именно строку с ключом G001. Поиск по контакту также может показать G007 с общим email — профили остаются разными.
4. В профиле показать визит в A, покупку в B, происхождение контактов и объяснимое предложение C.
5. В сегментах показать 5 подходящих, 3 неподходящих и 2 unknown-профиля.
6. Открыть email-кампанию. Из пяти участников один подходит для выгрузки; четыре исключены по разным причинам. Создать и скачать CSV. Платформа не отправляет сообщения.
7. В источниках нажать **«Добавить покупку в C»**. В истории станет 19 событий; G001 уйдёт из сегмента, рекомендация C исчезнет. Повтор той же загрузки даст дубль.

Демодаты генерируются относительно первого запуска и сохраняются при рестарте. Coverage — явно заявленный период полноты истории источника; его нельзя выводить из первой/последней покупки. Расчёт показывает дату общего среза. События вне выбранного временного окна остаются в ленте, но не относятся к этому срезу.

Все контакты синтетические. В пилоте нет реальной интеграции с CRM заказчика, провайдера отправки и справочника отписок. Частота ограничена по фактам выгрузки; priority — бизнес-приоритет, а не ML-вероятность.

## Сервисы

| Сервис | Назначение |
|---|---|
| web | Собранный React + Nginx; проксирует `/api` |
| init | Однократно применяет миграции и idempotent seed |
| api | HTTP API и бизнес-сервисы |
| worker | Принимает задания RQ и обрабатывает строки |
| dispatcher | Доставляет queued-задания из PostgreSQL и восстанавливает истёкшие lease |
| postgres / valkey | Основные данные / транспорт очереди |
| mock-source | Явно демонстрационный REST API кинотеатра |

API/worker/dispatcher/mock-source используют один backend-образ и общий код. Это модульное ядро с отдельными процессами, без распределённых копий профилей.

Данные и загрузки сохраняются в named volumes. Для штатной остановки:

```bash
docker compose down
```

Для возобновления:

```bash
docker compose up -d --wait
```

**Полный reset удаляет локальную базу, загрузки и историю выгрузок этого Compose-проекта.** Используйте его только когда действительно нужен чистый демостарт:

```bash
docker compose down -v
docker compose up -d --wait
```

Логи и состояние:

```bash
docker compose ps
docker compose logs --tail=100 api worker dispatcher
```

## Backend-проверки

Тесты используют отдельную PostgreSQL-базу с суффиксом `_test`; рабочая база приложения не очищается. Локально нужны Python >=3.13 и доступный PostgreSQL из Compose.

```bash
python3 -m venv .venv
.venv/bin/pip install -e 'apps/api[test]'
.venv/bin/pytest -q apps/api/tests
```

В CI задайте `TEST_DATABASE_URL`; его БД обязательно должна оканчиваться `_test`. Если порт PostgreSQL отличается от 55432, передайте изменённый URL. Тесты создают только выделенную тестовую базу; для этого используемый пользователь должен иметь CREATEDB.

Проверяются идентификация, tenant scope, auth/origin, три адаптера, ошибки строк, восстановление worker, контракт ответов, свежесть сегмента, покрытие истории, идемпотентность и гонки экспорта.

## Frontend и API-контракт

```bash
cd apps/web
npm ci
npm run generate:api
npm run build
```

Контракт: `docs/spec/02_OPENAPI.json`. Все 37 операций реализованы, включая управление покрытием источников и API радара. Сгенерированные типы: `apps/web/src/api.generated.ts`. Защищённые demo-операции служат явному импорту синтетических примеров и не являются коннекторами реальных данных.

Для frontend-разработки запустите API локально на 8010 и `npm run dev`: Vite проксирует `/api`. Избегайте одновременного запуска Vite и web-контейнера на 5180.

## Browser E2E в изолированном окружении

Тест не должен изменять демонстрацию, открытую пользователем. Для него отдельный Compose-проект, volumes и порты:

```bash
cp .env.e2e.example .env.e2e
docker compose -p hryukers-e2e --env-file .env.e2e up -d --wait
cd apps/web
npx playwright install chromium
npm run test:e2e
```

Вначале ожидается пустой каталог клиентских событий. Для повторного прогона удалите **только тестовые** volumes:

```bash
docker compose -p hryukers-e2e --env-file .env.e2e down -v
```

Команды Compose выполняются из корня репозитория. Playwright по умолчанию обращается к 5181; можно задать `E2E_BASE_URL`. Используются логин и пароль демопримера; другой пароль передайте в `DEMO_PASSWORD`. Скриншоты пишутся в `.data/qa/`, следы ошибок — в Playwright test-results.

## Развитие командой

Исходное ТЗ и пять промптов сохранены в `docs/spec/`. Общая модель находится в `apps/api/app/models`, обработчики — в `modules/ingestion`, сегментация — в `modules/segments`, экспорт — в `modules/exports`. HTTP-маршруты собраны в `main.py`; при расширении их удобно переносить в отдельные router модулей без изменения контракта.

Ближайшие продуктовые шаги: подтвердить формат реальных источников и общий ключ клиента, добавить интерфейс управления coverage поверх готового API, подключить справочник отписок и обратную связь о результатах кампаний. Изменения общей модели проводить через Alembic; расширения API синхронно отражать в контракте и TypeScript-типах.
