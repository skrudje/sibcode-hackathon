Ты реализуешь модуль импорта клиентской платформы «Хрюкерсы», кейс №2 SibКод. Нужен работающий код своего направления с проверками.

Полностью прочитай ТЗ и OpenAPI. Найди общий backend-каркас №2, его модели/DTO и инструкции репозитория. Не создавай собственные Customer/Event и альтернативную идентификацию. Если каркас ещё готовится, начни с адаптеров и их unit-тестов на согласованном NormalizedEvent, затем подключи общий сервис.

## Твоя зона

`apps/api/app/modules/ingestion/`, его router/services, Python entrypoints worker и dispatcher, тесты импорта. Python, Polars, openpyxl, HTTPX, RQ/Valkey. Изменения общих dependencies и Alembic передавай владельцу №2; требования Compose — участнику №5.

## Реализуй три разных источника

1. CRM CSV книжного C: поля из раздела 6.1, UTF-8/BOM, запятая.
2. POS XLSX кафе B: русские заголовки, первый лист; ID/контакты сохраняются текстом.
3. REST JSON кинотеатра A: fetch настроенного mock endpoint; nested customer, поля id/kind/timestamp/total.

Каждый адаптер выдаёт единый NormalizedEvent с корректным Decimal и aware datetime. Валидация суммы зависит от event_type. Отсутствие контакта допустимо. Сырые данные не определяют source_id/tenant_id и не выполняют код.

## HTTP и jobs

- POST файла и API sync возвращают 202 ImportJob по OpenAPI.
- GET imports, job и пагинированный отчёт rejected-строк.
- Лимит 10 MiB/10 000 строк; файл соответствует kind источника. API URL фиксирован конфигурацией, таймауты и сетевые повторы — по ТЗ.
- Приём файла сохраняет безопасно именованный файл в общий uploads volume и долговременную запись ImportJob.
- PostgreSQL — источник статуса. Dispatcher повторяет доставку queued в RQ при недоступности Valkey; отсутствие сообщения в транспорте не должно навсегда терять задание.
- Worker захватывает lease с token; heartbeat; восстановление после timeout; не более трёх попыток; защита от записи старым worker после потери lease.
- На каждую строку вызывай EventService из ядра. Результат строки и факты фиксируются согласованно. Успешные номера строк при повторе задания не обрабатываются заново.
- Счётчики вычисляются из ImportRowResult; исходные accepted после перезапуска остаются accepted. Статусы и арифметика — раздел 6.2.

Повтор файла новым заданием обрабатывается заново, но события становятся duplicate. Сетевые повторы worker не должны раздувать счётчики того же задания. Конфликт event ID сохраняет старую запись.

Coverage из metadata источника не вычисляй по минимальной/максимальной дате встреченного события. В P0 coverage задаёт seed; при приёме новой порции он не теряется.

## Стыковка

- №2 даёт NormalizedEvent, ORM и Identity/EventService; №3 не делает fuzzy matching.
- №5 поднимает mock-source, uploads volume, worker/dispatcher и генерирует fixtures с актуальными датами. Согласуйте команды запуска и адрес mock endpoint.
- №1 получает единый ImportJob и отчёт ошибок; не добавляй собственный формат прогресса.
- Пересчёт сегментов не реализуй отдельной системой: результаты читаются по актуальным событиям в запросах №4.

## Приёмка

- Все три адаптера на примерах дают одинаковую семантику данных.
- База после трёх импортов: 22 строки, 18 accepted, 1 duplicate, 3 rejected; 18 событий, 10 профилей. Конкретные количества каждого job есть в manifest.
- Неверная дата/отрицательная сумма/конфликт идентичности видны отдельно; другие строки приняты.
- Повторный импорт не создаёт событий; другой payload того же source/event ID даёт event_conflict.
- Прерывание worker посередине и временный отказ Valkey не теряют задание и не искажают итоговые счётчики.
- Получатель API видит корректные финальные статусы, причины и счётчики; в ответах и логах нет traceback/секретов.
