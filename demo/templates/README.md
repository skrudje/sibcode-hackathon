# Синтетические данные для демо

`demo_scenario.json` — IDs каталога, общий сегмент, правило, кампания, даты и ожидаемые количества.

Порядок базовой загрузки: API A (`api_A.json`) → POS B (`pos_B.xlsx`) → CRM C (`crm_C_initial.csv`). После проверки сегмента и экспорта загрузить `crm_C_after.csv`, затем повторить его. `crm_C_conflict.csv` проверяет конфликт одного ID события с другим amount; загружать только после `crm_C_after.csv`.

В CSV первая строка — заголовок, BOM допустим; в XLSX — один лист POS, все значения сохранены текстом, чтобы не потерять ID и телефон. API-ответ содержит массив events. Общего ключа в файлах нет: независимые локальные ID связываются по нормализованному телефону или email внутри ТЦ. Записи клиента 006 без корректных контактов намеренно остаются двумя профилями. Правила: [docs/IDENTITY.md](../../docs/IDENTITY.md).

Reference time примеров: 2026-10-31T05:00:00Z. Первый рабочий seed выбирает новый якорь Clock.now(), сохраняет его в Mall.demo_reference_time и сдвигает корректные даты согласно manifest; не меняет null-дату, отрицательную сумму и конфликт контактов. При рестарте якорь тот же, данные и история экспорта не перезаписываются. У тестов фиксированный Clock. Не выдавать sample-файлы за актуальные реальные сведения о посетителях.

Ожидаемые итоговые количества см. manifest и docs/IDENTITY.md. Некорректный email клиента 006 проверяет обработку ошибок контактов; остальные email принадлежат зарезервированному демонстрационному домену example.invalid. Реальные отправки не выполняются.
