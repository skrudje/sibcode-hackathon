# Хрюкерсы CDP — продуктовый бриф для creative lead

**Команда:** Хрюкерсы · **Хакатон:** SibКод, Сбер / Школа 21 · **Кейс №2:** единая рекомендательная клиентская платформа для торговых центров.

**Дата:** 31 октября 2026 года. **Формат продукта:** desktop-приложение для Windows и Linux. **Рабочее название:** «Хрюкерсы CDP»; название и визуальную айдентику можно развивать.

Документ объясняет продукт, его функциональность и бизнес-логику для проектирования интерфейса. Это описание рабочего инструмента маркетолога, а не сайта хакатона или презентации команды. Текущая вёрстка показывает функциональность, но не ограничивает будущий дизайн.

Для первого знакомства достаточно разделов 1–6, 15 и 22–23. Подробные правила собраны в разделах 9–18; состояния для макетов — в разделе 19.

## 1. Продукт за одну минуту

В торговом центре кинотеатр, кафе, книжный и другие арендаторы ведут собственные клиентские базы. Управляющая компания получает отдельные фрагменты истории и не видит, какие предложения разных арендаторов могут быть полезны одному посетителю.

Мы собираем данные арендаторов в общие профили, показываем историю взаимодействий, находим подходящие аудитории и помогаем подготовить приглашение в другое место торгового центра.

Пример: у посетителя есть событие в кинотеатре и покупка в кафе, но в доступной полной истории нет покупки в книжном. Маркетолог видит факты, действующее предложение книжного и может включить посетителя в аудиторию кампании.

Главная ценность — пройти путь **«разрозненные данные → понятная история клиента → обоснованная возможность → готовая аудитория»** в одном рабочем пространстве.

Центральная продуктовая фича — **«Радар новых визитов»**. Он сам находит наблюдаемые связи между арендаторами, объясняет их на конкретных клиентах и позволяет создать кампанию из найденной возможности.

Ожидаемый бизнес-эффект — облегчить подготовку релевантных приглашений и развивать взаимодействие посетителя с разными арендаторами. Рост продаж, конверсии и выручки пока не измерен; такие показатели нельзя показывать как достигнутый результат продукта.

## 3. Пользователи и их задачи

**Основной пользователь — маркетолог управляющей компании ТЦ.** Он работает с таблицами, предложениями арендаторов и аудиториями. Ему нужно понимать, кому, куда и почему можно предложить следующий шаг, и быстро подготовить результат для внешней системы рассылок.

**Дополнительный пользователь — аналитик или сотрудник, отвечающий за данные.** Он загружает файлы, проверяет ошибки и полноту истории, разбирается в происхождении событий и контактов. В MVP эти задачи выполняются в том же кабинете.

**Руководитель маркетинга — заинтересованная сторона.** Ему важно видеть доступную базу, состояние данных и обоснование решений. Отдельный кабинет руководителя и расширенные управленческие отчёты пока не реализованы.

**Арендатор — поставщик данных и предложения.** В текущем продукте у него нет собственного кабинета. Его интересы представлены через источник, события и предложение.

**Посетитель ТЦ — получатель пользы и потенциального приглашения.** Он не пользуется этим desktop-приложением. Приложение посетителя, кошелёк бонусов и личный кабинет покупателя в MVP не входят.

В реализации доступен рабочий кабинет маркетолога. Разные пользовательские портреты выше не означают, что уже существуют отдельные наборы прав и экраны для каждой роли.

## 4. Основные сущности простыми словами

| Сущность | Значение |
|---|---|
| Торговый центр | Контекст всей работы. Профили, источники, сегменты и кампании относятся к одному ТЦ |
| Арендатор | Кинотеатр, кафе, магазин или другой участник ТЦ |
| Источник | Конкретный поток данных арендатора: CSV из CRM, Excel из кассы, REST API |
| Загрузка / импорт | Отдельная попытка получить и обработать данные источника |
| Профиль клиента | Объединённая история посетителя и его контактов внутри одного ТЦ |
| Локальный ID | Идентификатор клиента в конкретной системе арендатора |
| Событие | Зафиксированные визит, покупка или бронирование с датой, арендатором и источником |
| Полнота истории | Явное заявление, что источник передал все события определённых типов за определённый период |
| Сегмент | Сохранённые условия отбора клиентов; состав вычисляется по актуальным данным |
| Предложение | Содержание приглашения к арендатору и срок его действия |
| Правило рекомендации | Связь сегмента, арендатора назначения, предложения и бизнес-приоритета |
| Возможность радара | Найденная связь арендаторов и аудитория, которую можно пригласить дальше |
| Кампания | Сегмент + правило рекомендации + канал подготовки контактов |
| Выгрузка | Сохранённый CSV с подходящими получателями на момент формирования |
| Дата среза | Момент, до которого проверяется история при конкретном расчёте |

Данные разных торговых центров не смешиваются даже при одинаковом телефоне или email. В MVP пользователь работает в своём ТЦ; переключатель между несколькими ТЦ пока не реализован. «ТЦ Орбита» — демонстрационный контекст, а не название самого продукта.

## 5. Главные сценарии

1. **Подготовить данные.** Открыть источники → загрузить CSV/XLSX или синхронизировать API → проверить результаты → исправить ошибки при необходимости.
2. **Разобраться в клиенте.** Найти профиль по имени, контакту или ID → посмотреть общую историю → увидеть происхождение контактов → понять рекомендацию.
3. **Собрать аудиторию вручную.** Создать сегмент из условий → проверить количество подходящих, неподходящих и неопределённых профилей → добавить предложение.
4. **Найти аудиторию через радар.** Выбрать связь → проверить объяснение и события клиентов → выбрать предложение → создать кампанию.
5. **Подготовить контакты.** Открыть кампанию → изучить исключения → сформировать CSV → сохранить файл через системный диалог.
6. **Проверить изменения.** Загрузить новую покупку → пересчитать аудиторию → увидеть, что клиент больше не подходит для прежнего приглашения.

Основная цепочка для демонстрации и кликабельного прототипа: **источники → профиль → радар → кампания → выгрузка → новая покупка → обновлённая аудитория**.

## 6. Общая организация desktop-приложения

Приложение устанавливается на компьютер, а данные и расчёты находятся на сервере команды. При запуске используется сохранённое подключение. Работа без сервера и автономная локальная база в текущий MVP не входят.

Основная навигация состоит из семи разделов:

1. Обзор.
2. Источники данных.
3. Клиенты.
4. Сегменты.
5. Рекомендации.
6. Кампании.
7. Радар новых визитов.

Дополнительно доступны настройки, справка, учётная запись и выход.

В текущей desktop-оболочке закреплены боковая навигация, верхняя панель инструментов и нижняя строка состояния. Прокручивается рабочая область. В каталоге клиентов поиск и пагинация остаются доступны при прокрутке таблицы. Это полезные свойства, которые нужно сохранить при переработке композиции.

Есть быстрый переход по разделам через `Ctrl+K`, сворачивание меню через `Ctrl+B`, переходы `Alt+1`…`Alt+7`, кнопка обновления данных. Фокус, выбор строки и открытые формы должны иметь понятные состояния; клавиатурные команды не должны мешать вводу текста.

Текущее окно по умолчанию — 1440 × 960, минимальное — 900 × 640. Желательно подготовить основной макет для 1440 × 960 и адаптацию для минимального размера. При уменьшении окна вторичная информация может сворачиваться, но основные действия должны оставаться доступны.

Текущая серверная дата хранится с часовым поясом; отображение в интерфейсе настроено на Красноярск, UTC+7. Рядом с важными периодами и датой среза нужен понятный контекст часового пояса. Настраиваемый пользователем часовой пояс пока не реализован.

## 7. Вход, запуск и настройки

### Вход

Экран содержит название продукта, email, пароль и действие «Войти». После успешного входа открывается рабочее пространство. Неверные данные дают понятную ошибку и позволяют повторить ввод.

Регистрация, восстановление пароля, приглашение сотрудников и управление правами через интерфейс пока отсутствуют. Не нужно делать их действующими частями основного прототипа без отдельного решения команды.

Серверная сессия ограничена по времени: сейчас 12 часов. При её истечении пользователь возвращается к форме входа. Истечение сессии нужно отличать от отсутствия сети.

### Недоступная платформа

Если на запуске сервер недоступен, показывается отдельное состояние «Не удалось подключиться» с коротким объяснением, кнопкой «Повторить» и доступом к настройкам. Это не ошибка пароля.

Если связь пропадает уже во время работы, состояние соединения должно быть заметно, а ошибки операций — понятны. Не следует выдавать ранее загруженные цифры за свежий успешный расчёт.

### Настройки

В новой версии настройки расположены внизу бокового меню и отдельно под формой входа. Диалог не открывается сам при каждом запуске. Сначала пользователь видит состояние рабочей платформы; поле адреса появляется после «Изменить сервер».

Новый адрес сначала проверяется. При неудаче остаются прежние настройки. Смена сервера требует нового входа; сохранение того же адреса не сбрасывает сессию. Пароли инфраструктуры пользователь здесь не вводит.

Адрес сервера и подсказки о локальной разработке — вторичная информация внутри настроек. Их не нужно выносить в заголовок основного рабочего экрана.

## 8. Экран «Обзор»

**Вопрос пользователя:** «Какие данные у нас есть и с чего начать работу?»

Основные показатели:

- Всего профилей клиентов текущего ТЦ.
- Всего событий в истории.
- Профилей с корректным телефоном или email.
- Источников данных.

Дополнительно показываются доля профилей с контактами, количество профилей без контактов, последние загрузки с результатами и несколько недавно созданных профилей.

Основные действия — загрузить данные, перейти к источникам, открыть радар или профиль. В демонстрационном режиме доступен явный запуск примера.

Процент профилей с контактами — показатель доступности контактов, а не точность идентификации, не процент успешных кампаний и не оценка достоверности личности.

Пустой обзор должен помогать сделать первую загрузку. Метрики без ответа сервера показываются как загрузка или отсутствие данных; их нельзя молча заменять правдоподобными демоцифрами.

## 9. Экран «Источники данных» и импорт

**Вопрос пользователя:** «Откуда пришла история и можно ли на неё опираться?»

### Карточка источника

Нужны арендатор, название источника, формат, дата последней успешной обработки, период полноты истории и типы событий, для которых полнота заявлена. Состояние загрузки и полнота истории — разные характеристики.

Сейчас поддерживаются:

| Источник | Действие |
|---|---|
| CRM / CSV | Выбрать и загрузить свой CSV; отдельно доступен демонстрационный пример |
| Касса / POS / XLSX | Выбрать и загрузить свой Excel; отдельно доступен демонстрационный пример |
| REST API / JSON | Запустить синхронизацию заранее настроенного источника |

Один источник относится к одному арендатору; в текущей модели у арендатора один источник. Конструктор новых интеграций, произвольное подключение CRM и создание/удаление источников из интерфейса пока отсутствуют. Демонстрационный REST-источник не означает готовую интеграцию с любой внешней CRM.

### Журнал загрузок

Для каждого задания нужны источник, дата, общее число строк, принятые строки, дубли, отклонённые строки и статус.

| Статус | Значение для пользователя |
|---|---|
| В очереди | Файл принят, обработка ещё не началась |
| Обработка | Идёт проверка и сохранение строк |
| Загружен | Все строки обработаны без отклонений; среди них могут быть дубли |
| Есть замечания | Часть строк принята или распознана как дубли, часть отклонена |
| Ошибка | Файл не прочитан, все строки отклонены либо обработка не восстановилась |

После приёма файла работа продолжается на сервере. Закрытие раздела не должно восприниматься как отмена импорта. Временный сбой обработки может привести к повторной попытке; уже обработанные строки не должны превращаться в новые покупки.

Пока задание активно, интерфейс обновляет его состояние. Необязательно показывать процент: точного общего количества строк в начале может ещё не быть.

### Ошибки

Нужно различать ошибку всего файла и замечания к отдельным строкам.

Ошибки структуры перечисляют конкретные проблемы: отсутствующие обязательные колонки, повторяющиеся названия, пустые заголовки, неверный разделитель или нечитаемый файл. Пример: «Отсутствуют колонки: event_type, event_time. Повторяется колонка: customer_id».

Для отклонённых строк доступны порядковый номер записи и понятная причина: некорректная дата, сумма, тип события, обязательное поле, неоднозначное сопоставление клиента или изменённое содержимое существующего события. В текущем отчёте нумеруются записи данных с 1; это не обязательно физический номер строки Excel с учётом заголовка.

Правильные строки могут сохраниться, даже если другие строки файла отклонены. Повторная загрузка исправленного файла распознаёт уже принятые события как дубли. Автоматического исправления неоднозначных данных и редактора ошибочных строк в приложении пока нет.

## 10. Сопоставление клиентов и качество контактов

Это актуальная логика общей ветки; дизайн должен отражать именно её.

1. Системы арендаторов используют собственные локальные ID. Общего заранее известного ID посетителя от них не требуется.
2. Внутри одного ТЦ запись связывается с существующим профилем при однозначном совпадении корректного **телефона или email**.
3. Email очищается от крайних пробелов и приводится к нижнему регистру. Точки и часть адреса после `+` сохраняются.
4. Телефоны приводятся к единому формату. Например, российские записи `8 (913) 123-45-67`, `79131234567` и `9131234567` дают один номер. Десятизначный номер трактуется как российский.
5. Если локальный ID ещё не связан с профилем и совпадений по контактам нет, создаётся новый профиль с внутренним ID. Совпадение имени и push-токена не используется для связывания.
6. Если контакты указывают на несколько профилей, строка отклоняется. Система не выбирает человека наугад и не добавляет из этой строки событие или контакты.
7. Локальный ID сохраняет связь с профилем, поэтому следующие события могут приходить без повторного телефона/email. Переключить уже идентифицированный локальный ID на другого человека обычным импортом нельзя.
8. Профиль без корректного телефона/email остаётся отдельным. Если позже для того же локального ID приходит однозначный контакт, его история может присоединиться к уже существующему профилю с сохранением происхождения данных.
9. Некорректный контакт может быть сохранён для диагностики, но не используется для сопоставления и выгрузки.
10. Общие ключи из старых файлов допускаются для совместимости, но не управляют сопоставлением. Внутренний ID профиля не нужно вводить пользователю вручную.

Два важных состояния:

- **«Есть контакты»** — есть корректный телефон или email; профиль пригоден для сопоставления и дальнейшей проверки сегмента.
- **«Нет контактов»** — корректного телефона/email нет; профиль и его события видны, но для сегмента он относится к «Недостаточно данных».

Нельзя подписывать первое состояние как «Личность подтверждена», «Проверен банком» или «100% совпадение». Это принятое командой правило связывания записей.

**Конфликт сопоставления** и **конфликт контактов для канала** — разные ситуации. Например, профиль мог корректно объединиться по телефону, но получить два разных email. Он остаётся единым профилем; email-выгрузка его исключает, а пригодность для SMS проверяется отдельно.

Происхождение каждого контакта сохраняется. Пользователь должен видеть, какой источник передал конкретное значение. Ручного редактора контактов и мастера слияния/разделения профилей в MVP нет. Неоднозначные исторические дубли также не сливаются автоматически.

## 11. Экран «Клиенты» и единый профиль

### Каталог

Поиск работает по имени, внутренней метке профиля, локальному ID источника, телефону и email. Есть фильтр «Все профили / Есть контакты / Нет контактов», таблица и постраничная навигация.

В строке достаточно показывать имя или «Без имени», внутренний ID, статус контактов и переход к профилю. Полные сведения раскрываются в карточке. Если поиск ничего не нашёл, следует предложить изменить запрос или проверить загрузку данных.

### Профиль

**Вопрос пользователя:** «Что известно об этом клиенте и почему ему подходит предложение?»

Профиль содержит:

- Имя, внутренний ID, статус контактов, количество событий и связанных ID источников.
- Ленту событий от новых к старым: тип, арендатор, дата и время, сумма и валюта при наличии, источник и ID исходного события.
- Контакты с каналом, исходным значением и источником; отдельные отметки некорректного формата и конфликтов.
- Связи с системами арендаторов: источник и его локальный ID клиента.
- Блок «Следующий шаг»: арендатор назначения, предложение, объяснение, дата среза и переход к кампаниям.

Визит, покупка и бронирование должны отличаться по подписи и визуальному обозначению. Бронирование не равно состоявшемуся визиту. Покупка с нулевой суммой допустима; ноль нельзя скрывать как отсутствие суммы.

Если рекомендации нет, нужно показывать причину: нет контактов для сопоставления, недостаточно истории, нет действующих предложений либо ни одно правило не подошло. Пустой блок не означает поломку.

## 12. Полнота истории и дата среза

Это одно из главных отличий продукта. Его нужно объяснить простым языком и сохранить в дизайне.

**«В файле нет покупки» не равно «клиент точно не покупал».** Возможно, источник передал только часть данных. Поэтому приложение может уверенно использовать отсутствие записи только при явно заявленной полноте истории.

Для источника отдельно задаются начало и окончание полного периода, а также типы событий: визиты, покупки, бронирования. Успешный импорт сам по себе не задаёт и не расширяет этот период. Программа не вычисляет его по первой и последней покупке файла.

Например: источник гарантирует все покупки с 1 июля по 30 октября. Это ещё не означает, что он гарантирует все визиты за те же даты.

Для сегмента с несколькими источниками расчёт использует общий срез, обычно самое раннее окончание их заявленных периодов. От этого момента отсчитывается окно сегмента. Если границы неизвестны, текущая реализация использует текущее время как срез, но без достаточной полноты результат всё равно будет неопределённым.

В расчёт входят события **после начала окна и до даты среза включительно**. История в профиле может содержать более новые и более старые события; это не означает, что они участвовали в конкретном расчёте.

В текущем расчёте недостаток покрытия хотя бы одного требуемого условия переводит профили в «Недостаточно данных», даже если отдельные события уже есть. Изменение покрытия влияет на сегменты и рекомендации без повторного импорта.

### Форма управления полнотой — нужно спроектировать

Нужны поля «Начало периода», «Окончание периода», понятный часовой пояс, выбор типов событий, сохранение, отмена и возможность отметить период неизвестным.

Ограничения: обе даты заданы вместе либо обе неизвестны; начало раньше окончания; окончание не в будущем; типы событий не повторяются. Пустой набор типов означает, что полнота не заявлена ни для одного типа.

Нужна короткая подсказка: «Укажите период, за который источник передал все события выбранных типов». Не следует создавать впечатление, что пользователь просто выбирает произвольный фильтр аналитики.

## 13. Экран «Сегменты» и правила отбора

**Вопрос пользователя:** «Кто соответствует моим условиям и на каких данных основан вывод?»

Сегмент содержит название, окно истории от 1 до 365 дней и две группы условий:

- **«Все эти события есть».** Клиент должен иметь событие у каждого указанного арендатора. Если в одном условии отмечены несколько типов, достаточно любого из них.
- **«Ни одного из этих событий нет».** У клиента не должно быть ни одного из отмеченных событий у соответствующих арендаторов за то же окно.

Пример: за 90 дней есть визит в кинотеатр A **и** покупка в кафе B; нет покупки в книжном C. Порядок событий A и B и посещение в один день не требуются. Сумма покупок, расстояние между событиями, частота и последовательность не являются отдельными фильтрами текущего конструктора.

Есть три результата оценки:

| Результат | Значение |
|---|---|
| В аудитории | Профиль пригоден для сопоставления, история полна, включающие условия выполнены, исключающих событий нет |
| Не подходят | Данных достаточно, но условия сегмента не выполнены |
| Недостаточно данных | Нет корректного телефона/email или недостаточно заявленной полноты истории |

Третью группу нельзя объединять со второй или показывать как «Не покупали». В аудиторию для кампании она не включается.

Сегмент динамический: сохраняются условия, а не неизменяемый список людей. При следующем расчёте новые события и новое покрытие могут изменить состав. Если покупка в C попадает в рассматриваемое окно, клиент перестаёт подходить для приглашения в C.

Экран показывает список сегментов, условия выбранного сегмента, дату среза, три счётчика и таблицу подходящих профилей. Доступны создание и редактирование. Отдельные списки всех неподходящих и неопределённых профилей сейчас не реализованы — для них возвращаются счётчики.

Конструктор должен предотвращать пустые типы события, противоречащие условия и повтор арендатора внутри одной группы. Сервер допускает до 10 условий суммарно, минимум одно включающее. Одинаковый арендатор может быть в обеих группах только с непересекающимися типами событий.

Если сегмент используется рекомендацией для C, нельзя убрать из него исключение покупки в C: такое редактирование нарушит смысл связанного предложения. Вместо молчаливого сохранения нужна понятная ошибка зависимости.

## 14. Экран «Рекомендации» и персональный следующий шаг

Раздел предназначен для настройки объяснимых бизнес-правил. Сейчас это не обучаемая модель и не генератор предложений нейросетью.

У правила есть название, сегмент, арендатор назначения, заголовок и описание предложения, начало и окончание действия, признак активности и приоритет от 1 до 100.

Предложение применяется, только когда правило включено, арендатор активен, текущий момент попадает в срок действия и клиент подходит под сегмент. Назначение обязательно должно быть исключено в сегменте по покупке: мы ищем аудиторию без зарегистрированной покупки у этого арендатора за выбранное окно.

Приоритет задаёт маркетолог. Он определяет порядок предложений, но не означает вероятность покупки или ожидаемую прибыль. Если одному арендатору соответствуют несколько подходящих правил, клиенту показывается одно наиболее приоритетное. Всего возвращается до пяти разных назначений.

Объяснение должно опираться на факты: какие события были, у каких арендаторов, за какой период не зарегистрирована покупка в месте назначения и на какую дату это проверено.

В списке правил нужны состояния «Действует», «Запланировано», «Срок истёк» и «Выключено» либо равноценное понятное представление. Они должны следовать реальным датам и активности, а не только цвету карточки.

Доступны создание и редактирование. Если правило уже используется кампанией, перенести его на другой сегмент нельзя: для другой аудитории создаётся новое правило. Отдельных удаления правил и редактора контента рекламного сообщения нет.

## 15. Экран «Радар новых визитов»

### Назначение

Маркетолог может не знать заранее, какую комбинацию арендаторов проверить. Радар перебирает группы из одного или двух исходных арендаторов и другого арендатора назначения. Для исходных мест учитываются зарегистрированные события тех типов, которые заявлены источниками; для назначения проверяются покупки.

Он отвечает на два вопроса: «У каких групп клиентов наблюдается более частое пересечение с этим арендатором?» и «Кого из похожей по исходным событиям группы ещё можно пригласить?»

Связь не требует, чтобы исходные события произошли раньше покупки в месте назначения. Это совместная встречаемость событий за период, а не восстановленный маршрут.

### Условия расчёта

- Только данные текущего ТЦ и активных арендаторов.
- Только профили, пригодные для сопоставления; после объединения веток подписи должны соответствовать модели «Есть контакты».
- Для каждого участвующего источника нужна успешная загрузка и полная история требуемых типов за общее окно.
- Участник считается один раз независимо от числа его чеков.
- У возможности должна быть ненулевая новая аудитория.
- Должны выполняться выбранные пороги числа общих клиентов и отношения частот.

Неполные источники показываются с объяснением и переходом к данным. Недостаток истории не должен выглядеть как отсутствие интереса посетителей.

### Что означают показатели

**Исходная группа** — клиенты с событиями во всех выбранных исходных местах. **Общие клиенты** — участники этой группы, у которых также есть покупка в месте назначения. **Новая аудитория** — участники исходной группы без зарегистрированной покупки в назначении за полное окно.

Базовая частота считается по активным профилям с хотя бы одним событием у активного арендатора за то же окно. Эта база включает исходную группу.

**Частота в группе = общие клиенты / исходная группа.**

**Базовая частота = покупатели назначения / активная база.**

**Отношение частот = частота в группе / базовая частота.**

Связи сортируются по отношению частот, затем по числу общих клиентов и размеру новой аудитории. Интерфейс показывает до 100 возможностей и общее число найденных. Этот отбор не является проверкой статистической значимости.

### Согласованный пример для макетов

Это иллюстративные синтетические данные, а не показатели реального ТЦ и не гарантия цифр в любой демобазе.

| Показатель | Значение |
|---|---|
| Активная база за окно | 100 клиентов |
| Есть события в кинотеатре A и кафе B | 40 клиентов |
| Из них покупали в книжном C | 25 клиентов |
| Всего покупателей книжного C в активной базе | 30 клиентов |
| Частота в группе | 25 / 40 = 62,5% |
| Базовая частота | 30 / 100 = 30% |
| Отношение частот | 62,5% / 30% ≈ 2,08× |
| Новая аудитория | 40 − 25 = 15 клиентов |

Корректная подпись: «В выбранной группе покупка в C встречалась в 2,08 раза чаще, чем в общей активной базе». Это не «вероятность покупки 62,5%» для оставшихся 15 клиентов и не обещание роста продаж в 2,08 раза.

### Состав экрана

Нужны фильтры окна истории, минимального числа общих клиентов и минимального отношения частот. Сейчас в интерфейсе доступны 30/90/180 дней, пороги 3/5/10/25 клиентов и 1,1×/1,5×/2×. По умолчанию — 90 дней, 3 клиента, 1,1×.

Основные области: карта связей арендаторов, список возможностей и панель проверки выбранной возможности. Карта и список должны давать доступ к одним и тем же действиям. Сложная графика не должна быть единственным способом выбора.

Панель проверки содержит:

- Исходные места и назначение.
- Размер новой аудитории.
- Две сравниваемые частоты с числителями и знаменателями.
- Отношение частот и простое объяснение.
- Полный период и дату общего среза.
- Кандидатов с раскрытием реальных событий и переходом к профилю.
- Примеры клиентов, у которых уже есть покупка в назначении и которые подтверждают наблюдаемую связь.
- Действующее предложение или объяснение, что его нужно добавить.
- Действие «Создать кампанию».

Наблюдаемая возможность может существовать без активного предложения, но создать кампанию из неё можно после выбора действующего предложения назначения. Перед сохранением сервер ещё раз проверяет данные и предложение: возможность могла устареть с момента открытия.

Создаются обычные динамический сегмент, правило и кампания. Затем пользователь попадает в предпросмотр контактов. Число клиентов в радаре и число пригодных контактов в кампании могут различаться.

Сейчас радар обновляет расчёт примерно раз в 10 секунд, пока открыт. Это периодический пересчёт, а не непрерывное наблюдение за людьми.

Визуальная метафора радара допустима, но продукт не использует геолокацию, видеонаблюдение, Wi-Fi-трекинг или физические маршруты. Стрелки обозначают направление предложения, а не путь человека по этажам.

## 16. Экран «Кампании» и подготовка получателей

### Создание кампании

Пользователь задаёт название, выбирает правило рекомендации и канал: email, SMS или push. Сегмент берётся из правила; произвольно выбрать несовпадающий сегмент нельзя.

Кампания — подготовка аудитории для внешней системы. В MVP нет редактора письма, календаря отправок, кнопки реальной отправки и статистики доставок.

### Предпросмотр

Сначала вычисляется текущий состав сегмента. Затем проверяется возможность использовать контакты для выбранного канала. Экран должен показывать переход **«Клиентов в сегменте → Готовы к выгрузке»** и объяснять разницу.

| Причина исключения | Что произошло |
|---|---|
| Предложение не действует | Правило выключено, срок не наступил/истёк либо арендатор неактивен |
| Нет контакта | Для выбранного канала нет корректного контакта; наличие телефона не гарантирует наличие email |
| Конфликт контактов | У одного профиля несколько разных корректных значений выбранного канала; система не выбирает одно автоматически |
| Повтор контакта | Один нормализованный контакт встретился у нескольких кандидатов; он не должен попасть в файл несколько раз |
| Уже выгружен | Этот контакт уже включался в выгрузку данной кампании |
| Ограничение частоты | Этот контакт в этом канале уже выгружался в течение последних 7 дней в другой кампании текущего ТЦ |

Причины показываются с количеством исключённых. Это последовательные проверки: одного кандидата не нужно одновременно прибавлять ко всем подходящим причинам. Если предложение не действует, все кандидаты исключаются по этой причине.

Предпросмотр показывает до 20 получателей с клиентом, контактом и предложением. Просмотр не резервирует аудиторию и не считается выгрузкой. Между просмотром и формированием файла результат может измениться из-за новых событий, другой выгрузки или окончания предложения.

### Формирование и сохранение CSV

При «Сформировать CSV» система заново проверяет текущую аудиторию и ограничения. Повтор одного и того же запроса после сбоя или двойного нажатия возвращает прежний результат, а не создаёт повторную выгрузку.

Если получателей нет, нужно показать причину и предложить проверить исключения. Пустой файл вместо успешной операции не создаётся.

После успеха сохраняются CSV, количество получателей, дата создания и дата среза. Фиксируется именно факт формирования выгрузки: он запускает ограничение частоты даже до скачивания файла.

В desktop скачивание открывает системный диалог «Сохранить как». Возможны сохранение, отмена и ошибка записи. Отмена сохранения на ноутбук не отменяет уже сформированную серверную выгрузку; пользователь может скачать её позже.

История выгрузок позволяет повторно скачать тот же файл. Повторное скачивание не создаёт кампанию, не пересчитывает старый файл и не продлевает ограничение частоты. Новые события меняют будущие расчёты, но не содержимое ранее созданного CSV.

В CSV находятся ID кампании и клиента, канал, контакт, арендатор назначения, заголовок предложения, объяснение и дата среза.

Отдельно нужно сохранить явную формулировку: **«Выгрузка не отправляет сообщения»**. Ограничение 7 дней считается по фактам выгрузок, а не по доставкам. Справочник отписок и интеграции с провайдерами рассылок пока не подключены.

## 17. Общие правила данных

Система работает с тремя типами фактов: визит, покупка и бронирование. Для каждого обязательны локальный ID клиента, ID события, тип и дата с часовым поясом.

Покупка требует неотрицательную сумму и валюту RUB; до двух знаков после точки. У визита суммы нет. У бронирования сумма необязательна, но сумма и валюта передаются вместе. Для новых валют и других типов событий интерфейс пока не должен обещать поддержку.

Событие определяется парой «источник + ID события». Повтор с теми же данными — дубль без повторной покупки. Если у существующего ID изменилось содержимое, новая строка отклоняется как конфликт; приложение не переписывает старую историю незаметно.

Данные из источника могут иметь разное качество. Ошибочный контакт, неоднозначное сопоставление, неполная история и недействующее предложение требуют разных сообщений и действий пользователя.

Программа не проверяет факт физического присутствия человека и не доказывает отсутствие посещения магазина. Корректный вывод — «нет зарегистрированной покупки за указанный период при заявленной полноте источника».

## 18. Справка по файлам для дизайна загрузки

Не нужно показывать формат данных на каждом экране. Он нужен рядом с выбором своего файла: в справке, шаблоне или раскрываемом блоке.

Ограничения: CSV и XLSX до 10 MiB, до 10 000 записей в одном задании. CSV — UTF-8 с запятой, первая строка — заголовки. Для XLSX читается активный лист с заголовками в первой строке. Пустой файл или таблица только с заголовком не считается успешной загрузкой событий.

| Поле | CSV | XLSX |
|---|---|---|
| ID клиента в источнике | `customer_id` | `id_клиента` |
| ID события | `event_id` | `id_чека` |
| Тип события | `event_type` | `тип_события` |
| Дата и время | `event_time` | `дата_операции` |
| Имя, необязательно | `full_name` | `имя` |
| Email, необязательно | `email` | `email` |
| Телефон, необязательно | `phone` | `телефон` |
| Сумма, нужна для покупки | `amount` | `сумма` |
| Валюта при наличии суммы | `currency` | `валюта` |

ID и телефоны желательно хранить текстом, чтобы Excel не удалил начальные нули. Пример даты: `2026-10-30T16:00:00+07:00`. Обычная дата Excel без часового пояса не подходит. Для времени события допускается небольшое отклонение вперёд — до пяти минут относительно сервера; заявлять полноту истории в будущем нельзя.

Пустые и повторяющиеся заголовки отклоняются; отсутствие обязательных колонок перечисляется явно. Старое поле общего ключа может присутствовать для совместимости, но пользователь не обязан его заполнять для объединения по контактам.

## 19. Состояния, которые нужны в макетах

| Область | Обязательные варианты |
|---|---|
| Запуск | Проверка сессии, форма входа, неверный пароль, платформа недоступна, повторная попытка |
| Рабочее пространство | Обычное окно, свёрнутое меню, быстрый переход, обновление, потеря связи |
| Обзор | Пустая база, загруженные данные, загрузка показателей, ошибка получения |
| Источник | Нет успешной загрузки; данные загружены; история полна, неизвестна или недостаточна для нужного окна |
| Импорт | Очередь, обработка, успех, частичный успех, ошибка файла, ошибки строк |
| Каталог | Результаты, пустая база, ничего не найдено, загрузка и ошибка |
| Профиль | Есть/нет контактов, некорректный контакт, несколько значений канала, есть/нет рекомендации |
| Сегмент | Подходит, не подходит, недостаточно данных; пустой сегмент; ошибка формы или зависимости |
| Правило | Действует, запланировано, истекло, выключено; недопустимое назначение |
| Радар | Нет данных, не хватает истории, нет связей при порогах, найдены возможности, нет предложения, возможность устарела |
| Кампания | Получатели есть/отсутствуют, разные причины исключения, пересчёт, предложение перестало действовать |
| Выгрузка | Формирование, успех, повтор того же запроса, отсутствие получателей, история файлов, отмена/ошибка сохранения |
| Настройки | Платформа доступна/недоступна, адрес скрыт/редактируется, проверка нового адреса, ошибка, успешная смена |

Ошибки должны говорить, что произошло и какое действие поможет: повторить запрос, исправить файл, уточнить полноту или добавить предложение. Достаточно короткого сообщения и деталей по запросу; технические коды не должны быть главным текстом.

Цвет не может быть единственным носителем смысла. У статусов нужны подписи, у значимых иконок — понятные названия, у интерактивных элементов — состояния фокуса, наведения, выбора и недоступности.

## 20. Демонстрационный режим

Данные для хакатона синтетические. Загружаются явно через отдельные действия и проходят тот же процесс проверки, что и обычные файлы. Цифры в интерфейсе вычисляются по фактическому содержимому базы.

Есть основной пример с кинотеатром, кафе и книжным, отдельный пример радара и действие добавления новой покупки для проверки пересчёта. Повтор примера не должен дублировать уже существующие события и не должен очищать историю выгрузок.

У деморежима нужна заметная, но спокойная маркировка. Действия «Загрузить пример» и «Добавить тестовую покупку» следует отличать от повседневной работы маркетолога. Их нельзя выдавать за подключённые реальные CRM или результаты кампаний.

Для одного согласованного кликабельного сценария можно использовать пример из раздела 15: аудитория 15 человек → проверка контактов → выгрузка → новая покупка одного участника → аудитория 14. Число пригодных контактов нужно задать отдельно и согласованно; сам радар этого числа не обещает.

## 21. Что не входит в текущий продукт

- Приложение посетителя, бонусный кошелёк, начисление баллов и полноценная программа лояльности.
- Настройка юридических согласий и договоров между партнёрами: в условиях кейса они предполагаются имеющимися.
- Реальная отправка email/SMS/push, конструктор сообщений, расписание рассылок, доставки и открытия.
- Измеренная дополнительная выручка, атрибуция результата и автоматический расчёт эффективности кампании.
- Обучаемые ML-рекомендации, предсказанная вероятность покупки и чат с AI-аналитиком.
- Геолокация, трекинг перемещений, карта этажей с реальными траекториями посетителей.
- Ручное объединение и разделение профилей, исправление контактов в кабинете, отмена принятого события.
- Свободный конструктор интеграций, управление арендаторами и создание новых источников через UI.
- Регистрация, восстановление пароля, управление сотрудниками и полноценная ролевая модель.
- Удаление сегментов/кампаний, архивирование, редактирование созданной кампании и отмена факта выгрузки.
- Полная офлайн-работа, синхронизация локальных баз и автоматическое обновление приложения.

Эти направления можно предложить как развитие, но в макетах MVP их нужно отделить от действующей функциональности. Приоритет — законченный путь от загрузки до объяснимой аудитории.

## 22. Направление дизайна и свобода creative lead

Продукт должен ощущаться как современный desktop-инструмент для работы с данными: собранный, понятный, быстрый и вызывающий доверие. Важны читаемые таблицы, устойчивые панели, ясные действия и возможность проверять происхождение выводов.

Желаемое ощущение — «я понимаю, что происходит, и могу принять решение». Технологичность лучше выражать через качество взаимодействия, карту связей, объяснение расчёта и реакцию на новые события.

Нужна визуальная иерархия: главный вывод → основное действие → доказательства → технические подробности. Число клиентов, пригодных для приглашения, важнее декоративного графика. Различия «клиенты», «события» и «контакты» должны считываться сразу.

Можно менять сетку, композицию, оформление навигации, представление карточек и таблиц, порядок второстепенных блоков и названия, если сохраняется смысл. Текущий набор разделов — функциональная карта, а не запрет на более удобную организацию.

Свободны выбор светлой/тёмной темы, палитры, типографики, иконографики, характера графики и айдентики. Название команды допускает лёгкий характер или маскота, но степень его присутствия в рабочем инструменте стоит выбрать осознанно.

Пользователь предложил [сайт SibКода](https://developers.sber.ru/kak-v-sbere/events/sib_kod) как визуальный референс. Его можно использовать при выборе настроения и подачи. В брифе нет требования буквально повторять страницу мероприятия или представлять продукт как официальный сервис Сбера.

Числа и проценты в макетах должны быть согласованы между экранами. Для персональных данных используем вымышленные примеры, например «Посетитель 001» и `visitor001@example.invalid`.

## 23. Что ожидаем от дизайна

1. Концепцию визуального языка: название/знак при необходимости, палитра, типографика, сетка, плотность данных и характер графики.
2. Общую desktop-оболочку с навигацией, панелью инструментов, состоянием соединения и быстрым переходом.
3. Все основные экраны: вход, обзор, источники и ошибки импорта, каталог и профиль, сегменты и конструктор, рекомендации и форма правила, радар и проверка возможности, кампании и выгрузки, настройки.
4. Форму управления полнотой истории источника с объяснением её смысла.
5. Набор повторяемых компонентов: таблицы, поиск, фильтры, пагинация, статусы, поля, даты, условия сегмента, карточки предложений, уведомления, модальные окна, панели деталей и состояния загрузки.
6. Варианты ключевых пустых, ошибочных, промежуточных и успешных состояний из раздела 19.
7. Адаптацию главных экранов для 1440 × 960 и 900 × 640, поведение прокрутки и длинных значений.
8. Кликабельный сценарий, показывающий бизнес-ценность: данные → профиль → возможность → кампания → файл → реакция на новую покупку.
9. Материалы для передачи в разработку: параметры компонентов, состояния, отступы, правила взаимодействия, тексты и экспортируемые ресурсы.

Если время ограничено, сначала стоит разработать оболочку, радар с подробностями и кампанию с причинами исключений. Они задают визуальный язык и показывают главное отличие продукта. Затем распространить систему на профили, импорт и конструкторы.

## 24. Как проверить, что дизайн сохраняет смысл

- Пользователь может объяснить, откуда пришли данные клиента и почему записи объединились.
- «Нет события», «не подходит» и «недостаточно данных» визуально и текстово различаются.
- Сразу понятны период анализа и дата среза.
- У рекомендации можно открыть фактическое обоснование.
- Показатель радара воспринимается как наблюдаемая связь, а не прогноз результата.
- Видно, почему из клиентов сегмента только часть стала контактами для выгрузки.
- Действие формирования CSV не воспринимается как отправка сообщений.
- Сохранённый файл и текущая динамическая аудитория не смешиваются.
- Техническая настройка сервера доступна, но не мешает обычному входу и работе.
- Основные действия доступны в минимальном окне и с клавиатуры.
