# Единый сбор взаимодействий и права

[Экран интеграций](screenshots/integrations.png)

Все новые записи содержат только **телефон (`phone`), email (`email`) и время взаимодействия (`time`)**. Нужен хотя бы один корректный контакт. Время обязательно, в ISO 8601 с часовым поясом. ID клиента и события вычисляет платформа. Имя, сумма и тип покупки не собираются.

Из трёх полей нельзя определить покупку, бронь или физическое присутствие. Создаётся событие `interaction`; новые сегменты и радар проверяют взаимодействия. Исторические события сохраняют свои типы, старые адаптеры оставлены для совместимости.

## Сценарий подключения

1. Администратор добавляет арендатора в «Интеграциях». Источник создаётся автоматически.
2. Арендатор предоставляет API: его собственная сторона читает нужные поля из CRM/БД. Прямого доступа desktop-клиента к чужой БД нет.
3. Администратор задаёт URL, интервал 1–1440 минут и при необходимости имя сохранённого серверного секрета. Подключение можно проверить без сохранения событий.
4. Dispatcher по расписанию создаёт долговременное задание; worker читает новые записи и сохраняет результаты строк. «Обновить» запускает тот же процесс вне расписания.
5. Повторный запуск переиспользует активное задание источника. Одинаковые записи не создают новые взаимодействия.
6. Свежесть, расписание и ошибки видны в интеграциях; подробности загрузок и строк — в источниках.

CSV/Excel с теми же тремя колонками подходят для первоначальной истории и разовых дополнений. У представителя бренда есть [отдельный кабинет](BRAND_PORTAL.md): он выбирает соответствующие колонки своей таблицы и передаёт данные только своего магазина. Общая клиентская база доступна сотрудникам УК. Для настоящего внедрения нужны API и доступ конкретного арендатора; HTTP-клиент и планировщик уже реализованы.

## Контракт API арендатора

Платформа делает GET на настроенный URL, затем передаёт параметр `cursor` из последнего полностью обработанного ответа.

```json
{
  "records": [
    {"phone": "+79131234567", "email": "visitor@example.invalid", "time": "2026-10-30T12:00:00+07:00"},
    {"phone": null, "email": "another@example.invalid", "time": "2026-10-30T12:15:00+07:00"}
  ],
  "next_cursor": "position-after-these-records",
  "has_more": false,
  "coverage_from": "2026-07-01T00:00:00+07:00",
  "coverage_to": "2026-10-30T23:59:59+07:00"
}
```

Пустой `records` означает успешный опрос без новых данных. `next_cursor` — непрозрачная строка позиции, не URL. При `has_more: true` читается следующая страница, при `false` позиция сохраняется после успешной обработки всех строк. Отклонённые строки не продвигают позицию: поставщик должен исправить их. Лимит цикла: 20 страниц, 10 MiB, 10 000 записей.

`coverage_from` и `coverage_to` необязательны. Это явная гарантия поставщика, что за период переданы все взаимодействия. Обе даты известны либо обе null, содержат часовой пояс; начало раньше конца, конец не в будущем. Гарантия применяется после успешной полной обработки. Без неё период задаёт администратор либо он неизвестен. Крайние даты записей не используются как гарантия полноты.

Повтор нормализованной тройки «телефон + email + время» в одном источнике считается дублем. Различить два разных взаимодействия с абсолютно одинаковыми тремя полями невозможно. Изменение набора переданных контактов меняет вычисляемый ключ — это ограничение минимального формата.

## Доступ к API

Домены перечисляются администратором сервера в `CONNECTOR_ALLOWED_HOSTS`. Внешние URL требуют HTTPS, HTTP разрешён только для доверенных локальных имён из `CONNECTOR_HTTP_HOSTS`. Перенаправления, встроенные логин/пароль и фрагменты URL запрещены. Для примера разрешены mock-source, localhost, 127.0.0.1.

Секрет задаётся на сервере, например `CONNECTOR_SECRET_KADR`. В интерфейсе указывается только его имя; worker отправляет значение в Bearer-заголовке. Допускается только префикс `CONNECTOR_SECRET_`, произвольные инфраструктурные переменные читать нельзя. Значения секретов не сохраняются в клиенте и не возвращаются API. В Compose переменная должна быть доступна backend-процессам через `.env`/серверное окружение.

Секрет обязательно назначается конкретному ТЦ, арендатору и origin на стороне сервера. Например, в `.env` (UUID замените своими, origin укажите без пути):

```dotenv
CONNECTOR_SECRET_STORE=your-private-token
CONNECTOR_SECRET_BINDINGS='{"CONNECTOR_SECRET_STORE":{"mall_id":"UUID-ТЦ","tenant_id":"UUID-арендатора","origin":"https://api.store.example"}}'
```

Список назначений не содержит значений токенов. Права проверяются при сохранении и перед каждым HTTP-запросом. Другой ТЦ, арендатор, домен, схема или нестандартный порт не могут использовать этот секрет. Существующие подключения с секретом нужно явно назначить; без назначения запрос не отправляется.

Адреса и имена секретов видит только администратор. Настройки нельзя менять во время активного импорта. Смена URL/секрета сбрасывает позицию; повторная загрузка одинаковой истории безопасна. Настройки и необязательный период полноты сохраняются одной транзакцией.

## Роли

| Действие | Маркетолог | Администратор |
|---|---|---|
| Профили, сегменты, рекомендации, кампании и CSV | Да | Да |
| Смотреть состояние подключений, загружать файлы, запрашивать обновление | Да | Да |
| Добавлять арендаторов, настраивать и проверять API, менять полноту | Нет | Да |
| Создавать сотрудников, менять роли и отключать доступ | Нет | Да |

Права проверяются сервером, данные ограничены текущим ТЦ. Смена роли/отключение действует и на текущую сессию. Изменить собственную роль и отключить себя через этот интерфейс нельзя. Пароли хешируются и не возвращаются в API.

Роль `brand` назначается администратором вместе с одним магазином своего ТЦ. После входа открывается отдельный кабинет: сопоставление колонок CSV/XLSX, проверка, импорт и журнал только своего источника. Общие `/customers`, `/sources`, `/imports`, сегменты, радар, кампании, экспорт и настройки ей недоступны даже через прямой запрос. Адрес API и полноту истории представитель не меняет.

Локальные аккаунты из `.env.example`: `marketer@example.com` / `HryukersDemo2026!`; `admin@example.com` / `HryukersAdmin2026!`. Изменение env после создания не переписывает существующий пароль.

## Заполненный пример

`SEED_WORKSPACE_DATA=true` подготавливает девять вымышленных арендаторов, около 600 клиентов и несколько тысяч взаимодействий. Начальная загрузка идёт через обычные задания и может занять несколько минут. Полнота появляется после полной обработки. Локальный API с вымышленными записями показывает работу настоящего опроса, но не означает наличие доступа к реальным CRM.

Повторная подготовка не очищает историю, кампании или выгрузки и сохраняет изменённые настройки подключения. Известные источники примера при первом включении переходят на новый формат; пользовательские источники не переименовываются. Служебные имена клиентов вычислены из контактов и не являются дополнительным собираемым полем.

Явное дополнение существующего локального окружения после миграций:

```bash
docker compose exec api python -m app.workspace_seed
```

## API платформы

- GET `/api/v1/integrations` — подключения, свежесть, расписания и ошибки.
- PATCH `/api/v1/integrations/{source_id}` — настройки и необязательная полнота; только admin.
- POST `/api/v1/integrations/{source_id}/test` — проверить HTTP и формат без импорта.
- POST `/api/v1/sources/{source_id}/sync` — обновить через обычное фоновое задание.
- POST `/api/v1/sources/{source_id}/imports` — загрузить CSV/XLSX.
- GET `/api/v1/integrations/template` — CSV-пример.
- POST `/api/v1/tenants` — создать арендатора и источник.
- GET/POST `/api/v1/team`, PATCH `/api/v1/team/{user_id}` — сотрудники и доступ.

Контракты синхронизированы с OpenAPI и TypeScript. Новых таблиц не требуется: используются существующие настройки источника и долговременные задания импорта.
