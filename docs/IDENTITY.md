# Сопоставление клиентов по контактам

Актуальное требование: источники арендаторов заранее не связаны. Для объединения истории достаточно совпадения нормализованного **телефона ИЛИ email** внутри одного торгового центра. Общий ключ, совпадение имён и push-токен для сопоставления не используются.

## Импорт

1. Адаптер получает локальный ID клиента источника, данные события и необязательные email/телефон.
2. Email очищается от крайних пробелов и приводится к нижнему регистру. Точки и `+suffix` в адресе не удаляются.
3. Из телефона убираются пробелы, скобки, дефисы и точки. Российские записи `8 (913) 123-45-67`, `79131234567` и `9131234567` становятся `+79131234567`. Десятизначные номера интерпретируются как российские; международные принимаются с `+` или `00`. Некорректные контакты сохраняются с происхождением, но не участвуют в сопоставлении и выгрузке.
4. Поиск ведётся среди контактов профилей текущего `mall_id`. Совпадение любого одного корректного контакта связывает запись с найденным профилем. Другой новый контакт дополняет профиль и сохраняется с источником.
5. Если найдено несколько профилей (например, email относится к одному, а телефон — к другому), строка отклоняется с `identity_conflict`. Новые события, контакты и связи из такой строки не сохраняются; причина доступна в журнале импорта.
6. При отсутствии совпадений создаётся профиль с внутренним ID `CDP-…`. Источникам этот ID знать не нужно. Поля `global_key`, `global_customer_key` и `единый_ключ` старых файлов допускаются для совместимости, но не управляют объединением.
7. Повторные события источника идемпотентны. Локальный ID сохраняет связь с профилем и позволяет загрузить событие даже без повторной передачи контактов. Попытка переключить уже идентифицированный локальный ID на другой профиль отклоняется.

Профиль без корректного телефона/email остаётся отдельным: совпадение имени не объединяет его с другим профилем. Если позже для того же локального ID приходит контакт, статус обновляется. Если контакт однозначно указывает на существующий профиль, локальная история присоединяется к нему с сохранением контактов и источников.

## Статусы и сегменты

Публичные имена полей API сохранены для совместимости:

- `verified` — в профиле есть корректный телефон или email; интерфейс показывает «Есть контакты». Это статус пригодности к сопоставлению, а не независимая проверка личности.
- `source_only` — нет корректного телефона/email; интерфейс показывает «Нет контактов». Для сегментов такой профиль получает `unknown`.
- `global_customer_key` в ответе — внутренний ID/сохранённая метка профиля, а не обязательный общий ключ источников.

Сегментация, полнота истории, действующие предложения и ограничения выгрузки продолжают проверяться независимо от способа сопоставления. Если профиль связан по телефону, но в нём два разных email, он остаётся единым профилем, а email-выгрузка исключает его с `contact_conflict`. Частота ограничивается по нормализованному контакту и каналу внутри ТЦ.

## Конкурентный импорт и обновление базы

Транзакционные блокировки резервируют локальный ID и нормализованные контакты до завершения строки. Два одновременных импорта одного контакта не создают два профиля. Контакты разных ТЦ не объединяются.

Миграция `6bc2e5a19041` нормализует уже сохранённые телефоны/email, обновляет статусы по наличию корректных контактов и добавляет индекс поиска. Существующие профили и выгрузки сохраняются. Неоднозначные исторические дубли не сливаются автоматически: при новом сопоставлении они дают `identity_conflict` и требуют разбора данных. Откат миграции удаляет индекс, но не восстанавливает прежнее форматирование контактов и статусы.

В активных демошаблонах общего ключа нет: API кинотеатра, POS Excel и CRM CSV используют независимые локальные ID. Посетитель 001 связывается по email/телефону, посетитель 004 — по телефону без email, посетитель 005 — по телефону с двумя разными email. Две записи посетителя 006 без корректных контактов остаются отдельными `unknown`. Предпросмотр email-кампании: 5 участников, 2 адресата, по одному исключению `missing_contact`, `contact_conflict` и `cooldown`.

Этот документ и фактическая реализация задают актуальные правила идентификации. Совместимость прежних адаптеров проверяется файлами в `apps/api/fixtures`.
