# Радар новых визитов

[Скриншот рабочего окна](screenshots/radar.png)

Радар предлагает маркетологу аудитории на основании наблюдаемых связей арендаторов. Он не отслеживает физические маршруты, не предсказывает вероятность взаимодействия и не доказывает дополнительный эффект кампании.

## Расчёт

Для каждого активного арендатора назначения с полной историей взаимодействий перебираются группы из одного или двух других арендаторов. Исходное условие — зарегистрированное событие одного из явно заявленных типов источника; бронь не называется совершённым визитом.

Каждая группа использует общий срез: минимальный `coverage_to` участвующих источников. Начало окна — срез минус выбранное число дней. Все источники должны иметь успешную загрузку, явно покрывать всё окно и необходимые типы событий. Покрытие не выводится из взаимодействий в файле.

В расчёт входят только профили с корректными контактами текущего ТЦ. Общая активная база — профили с хотя бы одним зарегистрированным событием активного арендатора в том же окне. Непрофили с корректными контактами показываются отдельно и не увеличивают статистику связи.

- Группа — клиенты с событиями во всех исходных местах.
- Общие клиенты — участники группы с взаимодействием у целевого арендатора.
- Частота в группе = общие клиенты / размер группы.
- Базовая частота = клиенты с взаимодействием целевого арендатора / общая активная база. Эта база включает исходную группу.
- Отношение частот (`lift`) = частота в группе / базовая частота.
- Аудитория — участники группы без зарегистрированной взаимодействия у целевого арендатора за полное окно.

По умолчанию: 90 дней, минимум 3 общих клиента, отношение частот от 1,1. Повторные транзакции одного клиента считаются один раз. Возможности без новой аудитории скрываются. Сортировка: отношение частот, число общих клиентов, размер аудитории; возвращаются первые 100 результатов с полным числом найденных возможностей. Это фильтр наблюдений, а не критерий статистической значимости.

Интерфейс показывает формулу, фактические числители/знаменатели, общий срез, события кандидатов и примеры профилей с взаимодействием в целевом месте. Карта и список доступны с клавиатуры. Проверка доступных данных обновляется каждые 10 секунд, пока открыт раздел.

## Кампания

Кнопка создания кампании открывает [единый мастер](CAMPAIGN_WIZARD.md) с условиями выбранной возможности. Маркетолог выбирает или создаёт предложение целевого арендатора, задаёт канал и проверяет контакты до сохранения. Старый API прямого создания кампании сохранён для совместимости. Для него маркетолог выбирает действующее предложение целевого арендатора и канал. Сервер повторно проверяет возможность и предложение; сегмент, правило и кампания сохраняются в одной транзакции. Ключ идемпотентности защищает от двойного нажатия, сетевого повтора и конкурентного создания.

Создаётся обычный динамический сегмент с теми же условиями. Его название описывает исходную группу, исключённые записи и окно истории; правило получает префикс «Правило:», а кампания сохраняет введённое маркетологом название. В форме создания видны условия аудитории и описание выбранного предложения. Новая взаимодействие исключает клиента при пересчёте. Кампания открывается сразу на нужной записи и использует существующие предпросмотр контактов, cooldown, блокировки и CSV-выгрузку. Сообщения не отправляются. Повтор с тем же ключом возвращает ранее созданную кампанию даже после изменения истории; другой запрос с уже использованным ключом получает 409.

## API

- `GET /api/v1/radar` — обзор; параметры `lookback_days` (1–365), `min_shared_customers` (2–1000), `min_lift` (1,01–100).
- `GET /api/v1/radar/opportunities/{opportunity_id}` — те же фильтры, `limit`/`offset`, аудитория и примеры реальных событий. Устаревшая или чужая возможность получает 404.
- `POST /api/v1/radar/campaigns` — `opportunity_id`, фильтры, `offer_rule_id`, `channel`, `name`, `idempotency_key`; 201 при создании, 200 при повторе. Устаревшая возможность или неактивный оффер получает 409.
- `POST /api/v1/demo/radar` — `stage: initial | followup`; явное создание заданий импорта синтетических файлов. Доступно только демонстрационному ТЦ, не изменяет coverage.

Контракт ответов находится в `docs/api/openapi.json`, типы фронта генерируются из него. Новых таблиц и миграций для радара не требуется. Аналитика прототипа выполняется в памяти после чтения данных текущего ТЦ; при переходе к большим объёмам нужны агрегаты в БД и фоновые расчёты.

## Проверка в интерфейсе

В заполненном примере доступны девять арендаторов с разными пересечениями аудиторий. Данные проходят обычные импорты. После их завершения откройте радар, выберите возможность и проверьте числители, знаменатели и события кандидатов. Создайте кампанию и сформируйте CSV. Затем загрузите в источнике назначения новую запись выбранного кандидата за рассматриваемый период: он выйдет из сегмента при пересчёте.

Радар использует `interaction` у новых источников. Для исторических источников сохранён прежний режим по покупкам; исторические факты не переименовываются. Название «новые визиты» — продуктовая метафора; физическое посещение по контактам и времени не определяется. Старые операции загрузки синтетического примера оставлены только для совместимости и не используются новым интерфейсом.
