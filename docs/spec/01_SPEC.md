# ТЗ на разработку MVP · «Хрюкерсы» · Кейс №2

Версия 1.0 · 31 октября 2026 года. Статус: согласуемая внутри команды основа реализации.

## 1. Продукт и результат

Создать веб-платформу для маркетолога управляющей компании торгового центра. Платформа объединяет события арендаторов в профиль посетителя, собирает аудитории по правилам и предлагает следующего арендатора с объяснением. Маркетолог выгружает аудиторию для внешней системы рассылок.

Главный демонстрационный путь:

> Импортировать три разных источника → увидеть объединённую историю → найти клиентов с визитом в кинотеатр A и покупкой в кафе B без зарегистрированной покупки в книжном C → объяснить рекомендацию C → выгрузить подходящие контакты → загрузить покупку в C → увидеть изменение сегмента и рекомендации.

### Обязательный объём P0

- Один пилотный ТЦ; три арендатора A/B/C; один тип пользователя — маркетолог УК.
- Авторизация; недоступность клиентских данных без сессии.
- CRM CSV, POS XLSX, REST API с JSON; отдельные адаптеры и демонстрация всех трёх.
- Валидация строк, отчёт об ошибках, идемпотентность событий, сохранение происхождения.
- Надёжное сопоставление профилей по согласованному общему ключу.
- Профиль и лента визитов, покупок и броней.
- Редактируемые правила сегментов и рекомендаций; объяснение результата.
- Кампания, предварительный просмотр и CSV-экспорт для email/SMS/push.
- Обработка нового события с изменением результата следующего запроса.
- Compose, синтетические данные, содержательные тесты и инструкция демонстрации.

### Вне P0

Реальная отправка сообщений; оформление согласий; программа лояльности; личный кабинет арендатора; машинное обучение; LLM в продуктовом контуре; конструктор произвольного SQL; ручное слияние профилей; отмены/возвраты; удаление и исправление уже принятых событий; промышленная отказоустойчивость и подключение настоящих CRM.

Согласия на обмен и обработку данных считаются существующими по условию кейса. Закрытый кабинет УК обеспечивает базовые границы доступа. Кнопки не должны имитировать работу, которой нет в backend.

## 3. Архитектура и границы модулей

Модульное backend-ядро с отдельными процессами API, worker и dispatcher. Они используют один Python-пакет, общие миграции и PostgreSQL. Valkey является транспортом задач; факты и долговременный статус импорта хранятся в PostgreSQL.

```text
React → REST API → PostgreSQL
               → запись задания в PostgreSQL
dispatcher → RQ/Valkey → worker → PostgreSQL
mock-source → HTTPX-адаптер worker
```

**Уточнение реализации:** в P0 сегменты и рекомендации вычисляются по запросу SQL/Python из текущих событий. Отдельного хранилища сегментов, фоновых проекций и очереди пересчёта рекомендаций нет. Это позволяет показать изменение сразу после фиксации импорта. Worker отвечает за тяжёлый импорт. Кешировать результаты сегментации в первой версии не нужно.

Модуль владеет изменением своих сущностей. Другие модули вызывают его сервис, а не копируют бизнес-правила. Общие ORM-модели размещены централизованно, чтобы агенты не создали несовместимые таблицы.

Внутренние точки стыка, которые №2 объявляет в каркасе:

- `IdentityService.resolve_customer(session, source_id, identity) -> Customer` — разрешить профиль или вернуть доменную ошибку; не выполнять commit внутри.
- `EventService.ingest_event(session, source_id, normalized_event) -> IngestResult` — атомарно обработать одну строку: `accepted`, `duplicate` либо `rejected` с кодом. Транзакцией строки управляет импорт.
- `SegmentService.evaluate(session, segment_id, as_of=None) -> SegmentEvaluation` — допустимые участники, статистика и причины неопределённости; поддержать фильтрацию по customer_id без копирования логики.
- `RecommendationService.for_customer(session, customer_id, as_of=None) -> RecommendationResult` — объяснимый результат.
- `ExportEligibilityService.preview(session, campaign_id) -> ExportPreview` — единые проверки для предпросмотра и фактической выгрузки.

Общие DTO: `NormalizedIdentity`, `NormalizedEvent`, `IngestResult`, `SegmentEvaluation`, `RecommendationResult`, `ExportPreview`. Их поля следуют разделам 5–9 и OpenAPI. Сервисы принимают `Session`; общую конфигурацию SQLAlchemy и способы транзакций задаёт №2. Для P0 использовать синхронные SQLAlchemy-сервисы; не смешивать `Session` и `AsyncSession` между модулями.

## 4. Общие соглашения HTTP

- Контракт: `02_OPENAPI.json`, OpenAPI 3.1. Все продуктовые маршруты начинаются с `/api/v1`.
- Имена JSON-полей: `snake_case`; UUID — строки; даты — ISO 8601 с часовым поясом, в ответе UTC.
- Деньги — decimal-строки, например `"450.00"`; не `float`.
- Списки: `items`, `total`, `limit`, `offset`. По умолчанию limit=20; предел 100.
- Стабильная сортировка: основной ключ + UUID. События: `occurred_at DESC, id DESC`; профили: `created_at DESC, id DESC`.
- В ошибки не отдавать traceback и содержимое секретов.

```json
{
  "error": {
    "code": "validation_error",
    "message": "Проверьте входные данные",
    "details": [{"field": "definition.lookback_days", "message": "Допустимо от 1 до 365"}],
    "request_id": "f5595f39-a26a-4bd1-9c42-f224e0a9bb82"
  }
}
```

Коды HTTP: 401 — нет сессии; 403 — запрещённый origin/действие; 404 — сущность не найдена в текущем ТЦ; 409 — конфликт состояния; 413 — превышен размер; 415 — неподдерживаемый файл; 422 — неверные поля; 503 — зависимость временно недоступна. Ошибка отдельной строки импорта не становится HTTP 500 для всего задания.

## 5. Предметная модель и хранение

Все бизнес-сущности принадлежат одному `mall_id`. Backend получает его из сессии; клиент не выбирает чужой ТЦ параметром запроса. Даже при одном ТЦ фильтр обязателен в запросах по идентификатору.

| Сущность | Минимальные поля и ограничения |
|---|---|
| Mall | id, name, timezone=`Asia/Krasnoyarsk`, demo_reference_time nullable; дата первого демо-seed, не продуктовая дата событий |
| User | id, mall_id, email, password_hash, role=`marketer`, is_active |
| Session | id, user_id, token_hash, expires_at; в БД не хранить открытый токен |
| Tenant | id, mall_id, code A/B/C, name, category, is_active; code уникален внутри ТЦ |
| Source | id, mall_id, tenant_id, name, kind=`crm_csv/pos_xlsx/rest_api`, covered_event_types, coverage_from, coverage_to, last_success_at, config |
| Customer | id, mall_id, global_customer_key nullable, display_name nullable, identity_status=`verified/source_only`, created_at |
| ExternalIdentity | id, source_id, external_customer_id, customer_id; unique(source_id, external_customer_id) |
| CustomerContact | id, customer_id, source_id, external_customer_id, channel=`email/sms/push`, value, normalized_value; хранить происхождение и не затирать конфликтующий контакт |
| Event | id, mall_id, tenant_id, source_id, customer_id, external_event_id, event_type, occurred_at, amount nullable, currency nullable, payload_hash, metadata, created_at; unique(source_id, external_event_id) |
| ImportJob | id, source_id, status, file_path nullable, total_rows nullable, accepted_rows, duplicate_rows, rejected_rows, attempt_count, lease_token nullable, lease_until nullable, heartbeat_at nullable, last_enqueued_at nullable, created_at, finished_at, failure_code nullable, failure_message nullable |
| ImportRowResult | id, job_id, row_number, status=`accepted/duplicate/rejected`, error_code nullable, error_message nullable, event_id nullable; unique(job_id, row_number) |
| Segment | id, mall_id, name, definition JSONB, created_at, updated_at |
| RecommendationRule | id, mall_id, name, segment_id, destination_tenant_id, priority 1..100, offer_title, offer_description, valid_from, valid_until, is_active |
| Campaign | id, mall_id, name, segment_id, recommendation_rule_id, channel, created_at |
| Export | id, campaign_id, idempotency_key, status=`ready`, recipient_count, as_of, file_content BYTEA, created_at; unique(campaign_id, idempotency_key) |
| CampaignRecipient | id, export_id, campaign_id, customer_id, channel, contact_normalized, exported_at; unique(campaign_id, channel, contact_normalized) |
| ContactChannelState | mall_id, channel, contact_normalized, last_exported_at; уникальный составной ключ; обеспечивает общий cooldown между кампаниями |

Общие требования:

- `global_customer_key` уникален внутри ТЦ, когда заполнен. Это согласованный идентификатор, а не модельная догадка.
- Время — `timestamptz`; сумма — `numeric(14,2)`; дополнительные атрибуты — JSONB. Ключевые фильтруемые поля не прятать только в JSONB.
- Сумма неотрицательна; для `purchase` обязательны сумма и `RUB`; у `visit` сумма и валюта null; у `booking` обе либо заполнены, либо null. Ноль покупки допустим.
- `coverage_from <= coverage_to`; отсутствие покрытия выражается двумя null. `covered_event_types` означает полноту доступной выгрузки этих зарегистрированных типов событий за период, а не наблюдение всех физических визитов.
- Индексы минимум: events(customer_id, occurred_at), events(tenant_id, event_type, occurred_at, customer_id), external identities unique, imports(status, lease_until), campaign recipient unique.
- В P0 источник закреплён за одним арендатором; для каждого арендатора в пилоте один активный источник.
- Настройки источника с API URL/секретами не возвращать целиком в browser. URL задан конфигурацией, свободный ввод произвольного URL через API не поддерживать.
- Исправления общей схемы оформляет №2 миграцией. Другие участники передают ему требуемую дельту.

### 5.1. Идентификация клиента

1. Нормализовать строковые ключи: trim; пустую строку считать null. Регистр `global_customer_key` сохранять. Ключ имеет смысл только внутри mall_id.
2. Найти существующую связь `(source_id, external_customer_id)`.
3. При существующей связи использовать её профиль, если переданный общий ключ отсутствует или совпадает. Если у профиля ключа ещё нет, его можно назначить только при отсутствии другого профиля с таким ключом. При противоречии — `identity_conflict`, не перепривязывать запись автоматически.
4. При новой внешней связи и наличии общего ключа найти/создать профиль с этим ключом и привязать запись. Статус `verified` означает доверие этому согласованному ключу.
5. При новой связи без общего ключа создать отдельный профиль `source_only`. Записи двух разных источников без общего ключа остаются разными профилями.
6. Телефон, email, имя и сходство поведения **не используются для автоматического слияния**. Одинаковый контакт может принадлежать разным профилям.
7. Новые контакты добавляются с происхождением; различные значения одного канала сохраняются как конфликт для выгрузки. В P0 нет автоматического выбора «более правильного» контакта.
8. Гонки создания общего профиля разрешаются ограничением уникальности и повторным чтением в транзакции. Ошибка уникальности не должна создавать второй профиль или частично принятый event.

### 5.2. Нормализованное событие

```json
{
  "external_customer_id": "POS-G001",
  "global_customer_key": "G001",
  "display_name": "Посетитель 001",
  "email": "g001@example.invalid",
  "phone": "+70000000001",
  "push_token": null,
  "external_event_id": "B-001",
  "event_type": "purchase",
  "occurred_at": "2026-10-21T05:00:00Z",
  "amount": "450.00",
  "currency": "RUB",
  "metadata": {}
}
```

`source_id` берётся из задания импорта; `tenant_id` — из источника. Входные данные не могут переопределить их. Обязательны внешний ID клиента, ID события, тип и дата. Имя и контакты необязательны; отсутствие контакта не является ошибкой события. События в будущем относительно `Clock.now()` отклоняются с допустимым рассогласованием часов 5 минут.

### 5.3. Повторные события

- Канонизировать нормализованные бизнес-поля и вычислить `payload_hash`; исключить порядок ключей JSON и форматирование decimal/времени из причин ложного конфликта.
- Совпали `(source_id, external_event_id)` и нормализованное содержимое — `duplicate`; никаких побочных изменений профиля и контактов.
- Ключ совпал, содержимое различается — `event_conflict`; старый факт не перезаписывать.
- Проверка идентификации, создание связей, контактов и события — одна транзакция строки; rejected не оставляет новый пустой профиль. Параллельный импорт того же события также не создаёт дубль.

## 6. Импорт и фоновые задачи

### 6.1. Три адаптера

| Источник | Приём | Входные поля |
|---|---|---|
| CRM книжного C | UTF-8 CSV, разделитель запятая; BOM допустим | customer_id, global_customer_key, full_name, email, phone, event_id, event_type, event_time, amount, currency |
| POS кафе B | XLSX, первый лист, первая строка — заголовки | id_клиента, единый_ключ, имя, email, телефон, id_чека, тип_события, дата_операции, сумма, валюта |
| API кинотеатра A | HTTP GET настроенного mock endpoint, JSON `{ "events": [...] }` | id, customer:{id,global_key,name,email,phone,push_token}, kind, timestamp, total, currency |

Полный пример каждого формата есть в `fixtures/`. Адаптер переводит свои поля в `NormalizedEvent`; проверка идентичности и вставка события едины для всех адаптеров. XLSX читать без исполнения макросов; xls/xlsm не поддерживаются. Не полагаться на автоматическое превращение ID и телефонов в числа.

Для P0 выбрать лимит 10 MiB на файл/ответ API и 10 000 строк/событий на одно задание. CSV/XLSX ограничиваются до постановки по размеру; количество и структура — при разборе в worker. HTTPX: таймаут 10 секунд, максимум три попытки на временную сетевую ошибку; переадресации не разрешать, URL mock-источника фиксирован в настройках.

### 6.2. Жизненный цикл задания

`queued → running → succeeded / completed_with_errors / failed`.

- `succeeded`: нет rejected, в том числе если все записи — дубли.
- `completed_with_errors`: есть rejected, а также хотя бы одна accepted/duplicate.
- `failed`: не удалось разобрать файл/получить API, все строки rejected либо пустой набор; причины сохранены.
- API после принятия задания возвращает 202 и ImportJob. Файл сохраняется в общем volume API/worker; путь генерирует сервер, имя пользователя не является путём.
- Запись ImportJob в PostgreSQL является долговременным запросом на обработку. Dispatcher опрашивает queued-задания, ставит ID в RQ и повторяет постановку после сбоя транспорта. Не считать `commit в БД + enqueue` одной атомарной операцией.
- Worker атомарно захватывает lease задания в БД. Только один актуальный lease_token может записывать результаты; heartbeat продлевает lease. Переходы состояния и записи результатов проверяют актуальный token.
- Для P0 lease=60 секунд, heartbeat не реже 10 секунд. Dispatcher возвращает зависшее running-задание в queued после окончания lease; максимум три попытки worker, затем failed. Просроченный worker не может продолжить запись с устаревшим token.
- `ImportRowResult` сохраняется в той же транзакции, что результат строки. При перезапуске уже завершённые номера строк пропускаются; итоговые счётчики считаются из сохранённых результатов. Не превращать прежние accepted в duplicate после повтора worker.
- Разбор файла детерминирован: row_number — номер записи начиная с 1, без строки заголовка. Одинаковый файл в новом задании повторно читается, его события становятся duplicate.
- Внутри одного задания строки обрабатываются последовательно в порядке row_number. Конкурентность допускается между заданиями; не распараллеливать конфликтующие строки одного файла.
- При финальном состоянии: accepted + duplicate + rejected = total_rows, если набор строк удалось разобрать. Ошибки синтаксиса файла допускают total_rows=null.
- Успешные строки сохраняются даже при ошибках других строк. Отчёт показывает номер и код ошибки; полный сырой контакт в тексте ошибки не нужен.

Минимальные коды ошибок строк: `missing_required_field`, `invalid_datetime`, `invalid_amount`, `invalid_event_type`, `identity_conflict`, `event_conflict`. Неподдерживаемые event_type отмен/возвратов отклоняются.

### 6.3. Полнота и актуальность

Coverage описывает заявленную полноту доступного источника; **не вычислять её автоматически по первой/последней покупке**. В пилоте metadata coverage задаётся синтетическим seed. После загрузки новой порции событий существующий coverage сохраняется; внешние реальные watermarks — дальнейшее развитие.

После завершения импорта браузер обновляет источники, профили, события, summary и открытые результаты сегментации/рекомендаций. Новые факты учитываются следующим запросом после commit; ожидание отдельного пересчёта не требуется.

## 7. Сегментация

### 7.1. Контракт правила

```json
{
  "lookback_days": 90,
  "include_all": [
    {"tenant_id": "UUID_A", "event_types": ["visit"]},
    {"tenant_id": "UUID_B", "event_types": ["purchase"]}
  ],
  "exclude_any": [
    {"tenant_id": "UUID_C", "event_types": ["purchase"]}
  ],
  "require_verified_identity": true,
  "require_complete_coverage": true
}
```

- `include_all`: каждое условие должно иметь хотя бы одно событие; внутри event_types действует OR.
- `exclude_any`: наличие хотя бы одного соответствующего события исключает профиль.
- Окно `(as_of - lookback_days, as_of]`; границы вычисляются в UTC.
- В P0 обе защитные опции всегда true: API не принимает false. UI не предлагает их отключать.
- Ограничить lookback_days диапазоном 1..365, число условий суммарно 1..10; include_all содержит минимум один элемент. Условия не содержат произвольный SQL или код.
- Все tenant_id принадлежат текущему ТЦ. Повтор одинакового арендатора внутри одного массива и пересечение include/exclude по одному типу событий — 422.

### 7.2. Дата оценки и трёхзначный результат

`as_of` можно передать явно; нельзя выбирать будущее относительно Clock.now(). По умолчанию взять минимальный coverage_to участвующих источников, ограниченный текущим временем. Так оценка привязана к доступному общему срезу, а не к случайной секунде после загрузки. При неизвестном coverage использовать текущее время и вернуть unknown для затронутых профилей. Ответ всегда содержит `as_of` и `evaluated_at`, UI показывает дату среза.

Порядок оценки каждого профиля:

1. `source_only` → **unknown**, причина `identity_unverified`.
2. Для каждого условия проверить покрытие всего окна и поддержку нужных типов событий источником арендатора. Если сведений недостаточно → **unknown**, причина `insufficient_history`.
3. При полном покрытии проверить include/exclude → **eligible** либо **ineligible**.

В список members попадают только eligible. Ответ содержит eligible_count, ineligible_count и unknown_count; сумма равна числу профилей текущего ТЦ. В P0 консервативно требуем полное покрытие всех условий перед проверкой предикатов, без частичных логических оптимизаций.

Слово «не был» в UI не использовать как установленный факт. Показать: «Нет зарегистрированных покупок в C за выбранный период». Coverage не означает, что известны покупки без идентификации клиента или вся его жизнь.

## 8. Рекомендации

Правило связывает сегмент, арендатора назначения и действующее предложение. Проверять, что тот же арендатор и event_type=`purchase` присутствуют в exclude_any сегмента: это демонстрирует приглашение к новому для доступной истории месту. При изменении сегмента повторно проверять зависимые правила; несовместимое изменение отклонить с 409 и перечнем rule_id.

Алгоритм на дату запроса:

1. Выбрать активные правила текущего ТЦ и активных арендаторов.
2. Проверить действие предложения по текущему `Clock.now()`, а не историческому as_of.
3. Оценить профиль по связанному сегменту на согласованном срезе.
4. Оставить подходящие правила. Для одного арендатора выбрать правило с наибольшим priority, при равенстве — с меньшим rule_id по строковому UUID.
5. Отсортировать по `priority DESC, destination_tenant_id ASC`; вернуть до пяти рекомендаций.

`priority` — заданный бизнесом приоритет 1..100, а не вероятность покупки или результат ML. В P0 не добавлять случайные баллы, embeddings и обращения к LLM.

Для каждой рекомендации вернуть правило, сегмент, арендатора, предложение, priority, explanation, observed_events и absence_checks. Выбрать по одному самому свежему событию на include-условие; при одинаковом времени — больший event_id. В absence_checks указать типы, период, observed_count=0, coverage_complete=true.

Пустой результат — нормальное состояние. Причины: `identity_unverified`, `insufficient_history`, `no_matching_rules`, `no_active_offers`. Если есть хотя бы одна рекомендация, empty_reason=null. При нескольких причинах без рекомендаций приоритет: identity → history → отсутствие активных предложений → отсутствие совпадений.

Наличие контакта не влияет на полезность рекомендации в профиле; оно влияет на возможность выгрузки.

## 9. Кампании и экспорт

Campaign содержит segment_id и recommendation_rule_id. Они должны ссылаться на один сегмент. Для профиля в кампании должно подходить именно указанное правило, даже если на экране рекомендаций показывается другое правило того же арендатора.

Каналы: `email` — email; `sms` — phone; `push` — push_token. Это три варианта CSV-выгрузки, а не интеграция с провайдером отправки. Контакты нормализовать: email trim/lower; телефон — trim и удаление пробелов/скобок/дефисов, результат `+` и 8..15 цифр; push — trim. Некорректный контакт не отклоняет событие, но не подходит для экспорта.

Валидность email в MVP — синтаксис, без DNS/MX-проверки: одна `@`, непустые части, точка в домене, отсутствие пробелов. Демодомен `example.invalid` должен проходить эту проверку. Не использовать проверку специальных/доставляемых доменов, которая отклонит синтетические примеры. Входные контакты в NormalizedEvent — optional string, а не EmailStr, отклоняющий всю строку события.

### 9.1. Предпросмотр

База — eligible members выбранного сегмента; base_count именно их количество. Не включать unknown в base_count. Для всей базы выполнить проверки в фиксированном порядке:

1. Предложение и арендатор активны: иначе всех исключить как `offer_inactive`.
2. Нет подходящего контакта канала — `missing_contact`; больше одного различного нормализованного валидного контакта канала — `contact_conflict`.
3. Среди оставшихся сгруппировать одинаковые контакты. Оставить профиль с минимальным global_customer_key (лексикографически), затем id; остальные — `duplicate_contact`.
4. Контакт уже экспортирован в этой кампании — `already_exported`.
5. Контакт был экспортирован в другую кампанию того же ТЦ и канала менее 7×24 часов назад — `cooldown`.

Каждый исключённый профиль получает ровно одну причину, поэтому base_count = eligible_count + сумма excluded_counts. В MVP нет отдельного справочника отписок: не выдумывать его наличие; это ограничение выводится в описании экспорта.

Предпросмотр возвращает counts и до 20 подходящих примеров. Превью не резервирует получателей и не изменяет историю. Фактический экспорт заново проверяет условия.

### 9.2. Фактический экспорт

- `POST /campaigns/{id}/exports`, обязательный заголовок `Idempotency-Key` с UUID.
- На первый успешный запрос создать Export и вернуть 201; повтор того же campaign_id/key возвращает тот же Export с 200 и тем же файлом, без повторных эффектов. Предварительно проверять idempotency_key до нового подсчёта.
- Использовать транзакцию со стабильным снимком для сегмента и событий; сериализовать экспорт одной кампании блокировкой её строки.
- Для защиты cooldown между разными кампаниями блокировать строки ContactChannelState в стабильном порядке; отсутствующую строку создавать через upsert. После получения блокировок повторно проверить ограничения контакта. Выбранный способ изоляции должен поддерживать корректный повтор транзакции при serialization failure.
- Запись recipient, обновление ContactChannelState и готовое CSV-содержимое Export фиксируются в одной транзакции. Для лимита 10 000 строк CSV можно хранить в BYTEA; файловой распределённой транзакции не требуется.
- Уникальные ограничения предотвращают повторный экспорт контакта в одной кампании при гонках.
- Если после повторной проверки нет получателей — 409 `no_exportable_recipients`; не создавать пустой Export и не занимать idempotency_key.
- Скачивание готового CSV ничего повторно не резервирует. Endpoint требует сессию и проверяет mall_id.
- Логируется факт **выгрузки**, не отправки и не покупки. Cooldown в P0 основан на выгрузках — обозначить это в UI.

CSV: UTF-8 с BOM, заголовки `campaign_id,customer_id,channel,contact,destination_tenant,offer_title,reason,as_of`. Экранировать CSV по правилам формата; пользовательские значения, начинающиеся с `=`, `+`, `-`, `@`, защищать от интерпретации формул табличным редактором. Для SMS-телефона также требуется такое безопасное представление в CSV; JSON сохраняет исходное нормализованное значение. Выгрузка содержит только поля выбранного канала и предложения.

## 11. Авторизация и эксплуатационный минимум

- Одна роль marketer, пользователь создаётся seed из DEMO_EMAIL/DEMO_PASSWORD. Нет публичной регистрации.
- Пароль хранится только хешем Argon2; случайный токен сессии имеет не менее 256 бит энтропии; в БД — его SHA-256; срок сессии 12 часов.
- Cookie `hryukers_session`: HttpOnly, SameSite=Lax, Path=/; Secure включён при HTTPS. Для локального HTTP разрешён Secure=false отдельной dev-настройкой.
- Browser и `/api` доступны с одного origin: Vite proxy в dev, reverse proxy web-контейнера в сборке. Мутации с cookie проверяют Origin по allowlist; без допустимого Origin возвращается 403. Backend-тесты явно задают Origin. Не включать CORS `*` с credentials.
- Logout отзывает сессию и удаляет cookie; истёкшая сессия — 401. Без сессии недоступны JSON клиентов, импорт и CSV.
- Без авторизации доступны login и `/api/v1/health/live`, `/api/v1/health/ready`. Готовность зависит от доступности PostgreSQL и Valkey; живость — от работающего процесса API.
- Логи содержат request_id, job_id, source_id, статусы и коды; пароли, session token и строки контактов не логировать.
- Секреты — environment; `.env.example` содержит шаблоны. Реальный `.env`, загруженные файлы и базы не коммитить.

## 12. Инфраструктура, данные и воспроизводимость

### Сервисы Compose

`web`, `api`, `worker`, `dispatcher`, `postgres`, `valkey`, `mock-source`.

API/worker/dispatcher используют один образ backend с разными командами запуска. Общий volume uploads доступен API и worker; PostgreSQL и Valkey имеют persistent volumes. Наружу достаточно опубликовать web; внутренние сервисы связываются по именам Compose. API напрямую можно открыть отдельным dev-профилем.

На старте: PostgreSQL healthy → единственный шаг миграций и idempotent seed → API ready → worker/dispatcher. Не запускать конкурирующие миграции из каждого процесса. Повторный запуск контейнеров сохраняет данные; полный reset — отдельная явно названная команда, не автоматический startup.

В README продукта обязательно:

1. Предварительные требования и копирование `.env.example`.
2. Запуск `docker compose up --build` и адрес интерфейса.
3. Учётная запись из заданных env без печати настоящего пароля в логах.
4. Создание/получение демонстрационных файлов.
5. Команды проверок и инструкция показа.
6. Остановка с сохранением данных и отдельный reset.

### Демосценарий

Манифест `fixtures/demo_scenario.json` определяет относительные даты и ожидаемые результаты. Вложенные CSV/XLSX/JSON — готовые примеры на фиксированную reference_time; seed должен уметь регенерировать их относительно текущего UTC. Для тестов внедряется Clock с фиксированным временем. Не привязывать рабочий алгоритм к октябрю 2026 года.

При первом seed сохранить выбранную reference_time в Mall.demo_reference_time. Даты файлов сдвигаются на разницу этой reference_time и даты sample-файлов. При обычном перезапуске использовать сохранённую reference_time, не сдвигать повторно файлы и не перезаписывать существующие источники, правила, кампании и историю контактов. Seed создаёт только недостающие демонстрационные сущности; новый временной якорь создаётся лишь при явном reset. Это сохраняет идемпотентность уже загруженных файлов и реальные результаты экспорта.

- Арендаторы: A — кинотеатр, источник REST JSON; B — кафе, POS XLSX; C — книжный, CRM CSV.
- История каждого источника: reference_time−120 дней .. reference_time. Source A покрывает visit/booking, B и C — purchase.
- Начальный сегмент: A/visit AND B/purchase AND NOT C/purchase; окно 90 дней.
- Предложение C активно относительно Clock.now(); priority=80.
- Канал основной демонстрационной кампании — email.
- До импорта можно создать только каталог, пользователя, сегмент, правило, кампанию и ContactChannelState для G008/email с last_exported_at=reference_time−1 день. Клиентские события загружаются тремя демонстрационными источниками.

Ожидаемые случаи:

| Ключ | История | Результат |
|---|---|---|
| G001 | A visit + B purchase; валидный контакт | В сегменте, рекомендация C, выгружается |
| G002 | A visit + B purchase + C purchase | Исключён из сегмента |
| G003 | Только A visit | Исключён: нет покупки B |
| G004 | A visit + B purchase, нет контактов | В сегменте; missing_contact при экспорте |
| G005 | A visit + B purchase, два разных email | В сегменте; contact_conflict |
| Без общего ключа, клиент 006 | A visit и B purchase под разными внешними ID | Два source_only профиля, unknown; автоматического слияния нет |
| G007 | A visit + B purchase, email совпадает с G001 | В сегменте; duplicate_contact после выбора G001 |
| G008 | A visit + B purchase; предыдущая выгрузка менее 7 дней назад | В сегменте; cooldown |
| G009 | A booking + B purchase | Исключён: бронь не считается визитом A в этом правиле |

В API A есть точный дубль и конфликт идентичности, а также запись без даты. В POS B есть отрицательная сумма. Полный манифест фиксирует количества.

| AC09 | Начальный сегмент: eligible=5 (G001/004/005/007/008), ineligible=3 (G002/003/009), unknown=2; рекомендации C есть у пяти eligible |
| AC10 | При неполном coverage C или неизвестном покрытии нужного типа отсутствует уверенное попадание в сегмент; unknown объяснён |
| AC11 | Превью email: base=5, eligible=1; missing_contact=1, contact_conflict=1, duplicate_contact=1, cooldown=1, остальные причины=0 |
| AC12 | Экспорт даёт один контакт G001; повтор того же Idempotency-Key возвращает тот же файл; новый key без новых адресатов — 409; повторное скачивание не меняет историю |
| AC13 | Два параллельных экспорта одной кампании не дублируют контакт; разные кампании соблюдают общий cooldown при гонке |
| AC14 | Загрузить дополнительную покупку C для G001: accepted=1, событий=19; сегмент eligible=4, ineligible=4, unknown=2; рекомендация C у G001 исчезла на следующем запросе |
| AC15 | Повторно загрузить тот же дополнительный CSV: duplicate=1, событий остаётся 19; payload с другим amount под тем же ID отклонён |
| AC16 | Просроченное предложение не рекомендуется и не экспортируется; empty_reason объясним, фиктивных процентов уверенности нет |
| AC17 | Реальный browser-путь Playwright: login → загрузки/статусы → профиль G001 → сегмент → превью → CSV → новое событие → обновление результата; моки выключены |

В разработке сначала покрыть ядро: identity, event dedup/conflict, сегмент AND/NOT с границами окна и coverage, контакты и идемпотентность экспорта. Добавлять проверки вокруг рисков и контрактов; не писать тесты, лишь повторяющие код.

## 14. Порядок сборки и владение общими файлами

| Артефакт | Владелец |
|---|---|
| OpenAPI, общие DTO, модели, Alembic, базовый main.py, Python dependencies | №2; изменения контрактов согласуются всеми затронутыми участниками |
| Frontend и npm lock | №1 |
| Import services, worker, dispatcher, отчёт строк | №3 |
| Предикаты сегментов и рекомендации | №4 |
| Кампании/экспорт, Compose, demo seed/fixtures, README, e2e | №5 |

До интеграционной фазы №2 подключает новые роутеры в main.py по заявке владельца модуля. На интеграционной фазе №5 может править общие файлы после согласования с владельцем и остановки параллельной правки этого файла. Каждый роутер экспортирует объект `router`; нет второго FastAPI-приложения внутри модуля.

Не создавать отдельные backend-сервисы для каждого участника, свои версии Customer/Event или собственные auth-механизмы. Агенты могут работать независимо по каталогам, но общая модель и контракт едины.

Готовность всей команды: все P0 и AC01–AC17 выполнены либо ограничение явно принято командой до защиты; нет скрытых TODO на основном пути, демо воспроизводимо с чистого старта, данные не остаются только в frontend-моках.
