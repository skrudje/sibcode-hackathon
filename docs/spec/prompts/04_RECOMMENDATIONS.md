Ты отвечаешь за сегментацию и рекомендации платформы «Хрюкерсы», кейс №2 SibКод. Нужна проверяемая реализация с реальными SQL/Python-вычислениями.

Полностью прочитай ТЗ и OpenAPI, особенно разделы 7–9. Изучи существующие модели/DTO/Clock №2 и инструкции репозитория. Не создавай свои таблицы Customer/Event и отдельную БД.

## Твоя зона

`apps/api/app/modules/segments/`, `modules/recommendations/`, их router/services/tests. Используй PostgreSQL, SQLAlchemy Session и Python. HTTP-имена строго по OpenAPI; изменения общих моделей/миграций проводит №2.

## Сегменты

1. Список, создание, чтение, полное изменение через PUT и пагинированные eligible members.
2. Definition содержит lookback_days, include_all, exclude_any и две обязательные true-защиты. AND между include-условиями, OR между типами одного условия и между exclude-условиями.
3. Окно `(as_of-lookback_days, as_of]`, UTC. Default as_of привязан к общему watermark источников; возвращай as_of и evaluated_at.
4. Три результата: source_only → unknown; неполное покрытие → unknown; при полном покрытии — фактические предикаты eligible/ineligible. Суммы статистики соответствуют всем профилям ТЦ.
5. Проверяй принадлежность арендаторов ТЦ, ограничения числа/типов условий, пересечения include/exclude и зависимые recommendation rules при изменении сегмента.
6. Не выдавай отсутствие данных за отсутствие покупки. Дата первой/последней покупки не доказывает coverage.

## Рекомендации

- Реализуй list/create/update recommendation rules и customer recommendations по контракту.
- Предложение имеет назначение, связанный сегмент, срок, priority и активность.
- Назначение должно быть исключено по purchase в сегменте. При несоответствии не сохраняй правило/несовместимое изменение сегмента.
- Используй один SegmentService и для списка members, и для рекомендаций конкретному профилю, и для экспортного сервиса участника №5.
- Проверяй срок оффера по текущему Clock.now(); историю анализируй на as_of. Эти два времени не взаимозаменяемы.
- Сортировка и дедупликация назначения детерминированы по разделу 8. Priority — число бизнеса, не ML confidence.
- Верни наблюдаемые события, проверки отсутствия, источники оснований через event_id/tenant_id и понятный русский explanation. Выбирай свежие события с согласованным tie-break.
- Пустой результат объясняется empty_reason; не генерируй вымышленные рекомендации ради непустого экрана.
- Контакты не влияют на рекомендацию в профиле; пригодность для экспорта проверяет №5.

В P0 не нужны LLM, embeddings, обучение модели и отдельное хранилище сегментов. Каждый следующий запрос читает актуальные принятые события. Избегай N+1 там, где условия можно посчитать SQL EXISTS/NOT EXISTS; при этом сначала обеспечь правильную семантику.

## Стыковка

№2 предоставляет ORM, DTO, Session и Clock. №1 использует твои маршруты для форм и профиля. №5 вызывает общий SegmentService и проверку конкретного recommendation rule для кампании. Не заставляй экспорт повторять SQL-правила самостоятельно; дай явный внутренний метод проверки указанного rule_id.

## Проверки

- AND/OR/NOT; покупка C исключает профиль; booking A не считается visit A.
- Нижняя граница окна исключена, верхняя включена; время с часовым поясом нормализовано.
- Source_only, неизвестная история и непокрытый event type дают unknown, а не false positive.
- Базовый manifest: eligible=5, ineligible=3, unknown=2, рекомендации C у пяти eligible.
- После покупки C/G001: eligible=4, ineligible=4, unknown=2; у G001 нет рекомендации C без ожидания фонового пересчёта.
- Неактивный/просроченный оффер, несколько правил одного назначения, одинаковые priority и пустой результат.
- Обновление сегмента не оставляет несовместимое связанное правило.
