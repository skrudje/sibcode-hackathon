# Промпт участнику №2 · Backend-ядро и общая модель

Скопируй текст ниже в свою нейронку и приложи `01_SPEC.md`, `02_OPENAPI.json`, папку `fixtures/` и доступ к общему репозиторию.

---

Ты отвечаешь за backend-ядро клиентской платформы «Хрюкерсы», кейс №2 SibКод. Нужна реализация кода, а не только архитектурное описание.

Сначала полностью прочитай общее ТЗ и OpenAPI, изучи инструкции и существующие файлы репозитория. Ты владелец общих моделей, миграций и backend-каркаса. Не переписывай каталоги других участников.

## Твоя зона

`apps/api/app/core/`, `models/`, `contracts/`, `modules/auth/`, `modules/catalog/`, `modules/customers/`, `alembic/`, первоначальный `main.py` и общие Python-зависимости. Стек: Python 3.13, FastAPI, Pydantic 2, SQLAlchemy 2 с синхронным Session, PostgreSQL 18, Alembic, psycopg.

## Первый результат — общий каркас

Сделай его до глубокого развития собственной части, чтобы остальные могли интегрироваться:

1. Один Python-пакет app; конфигурация из env; Session factory; единый Clock; доменные ошибки с request_id и общими exception handlers.
2. ORM всех таблиц раздела 5, ограничения/индексы и начальная миграция. Включая импорт, сегменты, кампании и экспорт, логика которых принадлежит другим участникам.
3. DTO/протоколы NormalizedIdentity, NormalizedEvent, IngestResult, SegmentEvaluation, RecommendationResult, ExportPreview. HTTP-схемы соответствуют OpenAPI; внутренние поля уточняются по ТЗ.
4. Единая точка подключения объектов router модулей. Не создавай второй FastAPI-сервер для чужих модулей. Не подменяй отсутствующую реализацию успешными заглушками.
5. Согласованная структура backend dependencies и пример env для интегратора.

После каркаса реализуй ядро:

- Cookie-сессии, login/logout/me; Argon2; хеш токена в БД; истечение сессии; проверка origin и tenant scope.
- Каталог tenants/sources без раскрытия приватной конфигурации источников; summary.
- Поиск и профиль клиента, контакты с происхождением, внешние ID, лента событий с пагинацией.
- IdentityService по разделу 5.1: только подтверждённый global_customer_key и существующие внешние связи. Телефон/email/имя не склеивают профили.
- EventService.ingest_event по разделам 5.2–5.3: единый путь всех адаптеров, транзакция строки, canonical payload hash, duplicate/event_conflict, отсутствие побочных профилей при rejected.
- Нормализация контактов как общая функция для импорта и экспорта; хранение конфликтующих валидных контактов без тихого перезаписывания.

## Обязательные точки стыка

Объяви сигнатуры из раздела 3 ТЗ. IdentityService и EventService принимают Session и не делают скрытого commit; транзакцией строки управляет №3. Согласуй с ним способ результата rejected: доменная ошибка/результат должны позволять откатить всю строку и сохранить её отчёт отдельно без частичных side effects.

№4 использует твои модели Event/Customer/Source и общий Clock. №5 использует авторизацию, Session, модели Campaign/Export/ContactChannelState и DTO. Их сервисы реализуют они; не пиши вторую версию их логики.

Счётчики summary читают реальные факты PostgreSQL, а не константы manifest. Seed данных реализует №5, но использует согласованные модели/сервисы.

## Значимые проверки

- Миграция применяется на пустой PostgreSQL; ограничения реально срабатывают.
- Сессия: вход, неверный пароль, logout, истечение, отсутствие сессии, чужой mall_id через ID и недопустимый origin.
- Два источника с одним global key дают один профиль. Совпавший контакт без ключа — два профиля. Противоречивый ключ — отказ.
- Повторный и конкурентный импорт одного события не создаёт дублей. Изменённое содержимое того же ID не перезаписывает историю.
- Отказ строки не оставляет созданных клиентов/связей/контактов. Контакты не затираются при противоречии источников.
- Поиск и лента соблюдают контракт, tenant scope и стабильную пагинацию.

Ты не владеешь frontend, Compose, алгоритмом рекомендаций и реализацией worker. В main.py подключай их готовые router по заявке. При необходимости изменить общее API сначала предложи командную правку ТЗ/контракта.

В конце дай список файлов, миграций и внутренних интерфейсов, команды проверки, фактические результаты и оставшиеся зависимости от других участников. Отдельно укажи готовность общего каркаса к использованию.
