## Твоя зона

`apps/api/app/modules/campaigns/`, `modules/exports/`, `infra/`, `demo/`, Compose, `.env.example`, README, `tests/e2e/` и свои backend-тесты. Общие модели и миграции создаёт №2; предложи ему точную дельту, не заводи независимую схему.

## Кампании и экспорт

1. Campaign list/create/detail, preview, list/create exports и protected CSV download по OpenAPI.
2. segment_id и recommendation_rule_id согласованы. Для кампании проверяется именно заданное правило, не случайная первая рекомендация профиля.
3. Один ExportEligibilityService для preview и create. Фиксированный порядок исключений: offer → missing/conflicting contact → duplicate contact → already_exported → cooldown. Одна причина на профиль; base_count равен eligible members сегмента.
4. Каналы email/sms/push выбирают свой контакт. Нормализацию бери из общего ядра. Несколько валидных значений одного канала — conflict, не выбирай удобный сам.
5. Для одинакового контакта выбери профиль по global_customer_key ASC, затем id. Cooldown 7 дней действует между кампаниями в рамках ТЦ/канала и основан на выгрузках.
6. POST export с Idempotency-Key: первый ответ 201, повтор того же ключа 200 с тем же Export/CSV; при отсутствии адресатов 409, без пустого файла и побочных записей.
7. Реализуй транзакции и блокировки кампании/ContactChannelState, уникальные ограничения, повтор транзакции при необходимом конфликте сериализации. Два параллельных запроса не обходят повторы и cooldown.
8. CSV хранится готовым BYTEA в Export в той же транзакции, что получатели и contact state. GET скачивает прежний файл без новых эффектов. UTF-8 BOM, согласованные колонки и защита от spreadsheet formula injection.
9. Вся выгрузка защищена сессией и mall scope. Никакой реальной отправки SMS/email/push.

## Инфраструктура

- Compose: web, api, worker, dispatcher, postgres, valkey, mock-source. API/worker/dispatcher используют один backend-образ с разными командами.
- Внешняя точка входа web; проксирование /api на backend. Зафиксированные зависимости и воспроизводимая сборка.
- PostgreSQL/Valkey persistent volumes; общий uploads для API/worker; healthchecks и корректный startup order.
- Миграции/seed выполняются одним шагом, не всеми процессами одновременно. Рабочая остановка не удаляет данные; reset — отдельная явная команда.
- Liveness/readiness реализуй с использованием общих настроек ядра. Readiness не должна сообщать OK при недоступной БД/Valkey.
- Пример env без реальных секретов; команды тестов; README первого запуска и демонстрации.

## Демоданные и mock-source

- Используй IDs и ожидаемые результаты `fixtures/demo_scenario.json`.
- Seed idempotent: каталог, источник с coverage, пользователь, сегмент, recommendation rule, кампания, contact state G008. Не подгружай скрыто все события в БД: команда должна показать три реальных импорта.
- При первом seed выбери Clock.now() как reference_time и сохрани её в Mall.demo_reference_time; сдвинь корректные даты sample-файлов относительно неё. При рестарте используй тот же якорь и не перезаписывай факты/экспортную историю. Сохраняй некорректную дату, отрицательную сумму, дубль и identity conflict. Regeneration описана в manifest.
- Mock REST endpoint возвращает api_A.json и доступен worker по имени сервиса. Это явно демонстрационный источник, не мнимое подключение настоящей CRM.
- Дополнительный CSV покупки C/G001 и конфликтный CSV должны быть доступны для показа; повторная генерация не меняет бизнес-смысл тестов.

## Приёмка и интеграция

По мере готовности частей собирай вертикальный путь: login → один импорт → профиль → три источника → сегмент → рекомендация → экспорт → покупка C → изменение результата.

Проверь AC01–AC17, особенно точные количества manifest, защищённость CSV, идемпотентность и параллельные экспорты. Интеграционные проверки используют настоящую PostgreSQL; E2E — Playwright с выключенными frontend-моками.

До интеграционной фазы общим main.py владеет №2. После согласования остановки параллельных правок ты можешь подключать роутеры и исправлять стыки. Не меняй общее API молча и не заменяй чужой модуль своей несогласованной реализацией. Рутинные дефекты в своей зоне исправляй самостоятельно.

В конце предоставь адрес/команды запуска, сценарий показа на 5–7 минут, выполненные проверки с результатами, список оставшихся ограничений и статус каждой интегрируемой части. Не утверждай, что система готова целиком, если она работает только на моках.
