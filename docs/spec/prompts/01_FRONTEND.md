Ты отвечаешь за frontend продукта команды «Хрюкерсы», кейс №2 хакатона SibКод. Нужно реализовать работающий кабинет маркетолога клиентской платформы ТЦ. Создай код своего направления и проверь его, не ограничивайся описанием подхода.

Сначала полностью прочитай приложенные `01_SPEC.md` и `02_OPENAPI.json`. Бизнес-правила и HTTP-поля уже согласованы: не переименовывай их по своему усмотрению. Изучи существующий репозиторий и его инструкции; сохрани работу других участников.

## Твоя зона

Весь `apps/web/`: React, TypeScript, Vite, React Router, Tailwind CSS, shadcn/ui, TanStack Query. Владеешь frontend package.json и lock-файлом. Общие backend-модели, миграции, Compose и OpenAPI принадлежат другим участникам.

## Что реализовать

1. Приложение с маршрутизацией, layout, боковой навигацией, авторизацией через cookie-сессию и обработкой 401.
2. Типизированный API-клиент по приложенному OpenAPI. Базовый путь `/api/v1`; credentials включены. Экспорт возвращает JSON с download_url, а не CSV в теле POST.
3. Обзор: числа профилей/событий/источников, качество идентификации, последние импорты.
4. Источники: три вида, coverage; загрузка CRM CSV и POS XLSX, запуск API sync; состояние задания и отчёт отклонённых строк.
5. Поиск и список клиентов; профиль с внешними идентификаторами, происхождением контактов, конфликтами, историей событий и объяснимыми рекомендациями.
6. Сегменты: список, создание, полное редактирование через PUT, конструктор ограниченных условий; дата среза, eligible/ineligible/unknown и members с пагинацией.
7. Правила рекомендаций: форма выбора сегмента и арендатора C, предложения, срока, priority и активности. Priority не показывать как вероятность.
8. Кампании: создание, preview, причины исключения, CSV-экспорт и история готовых выгрузок. Preview не означает отправку. Показывать ограничение о неполном контроле отписок и о cooldown по выгрузкам.

## Поведение и качество

- Оформление: тёмный #101114, белый, синий #2466F6, светлые карточки; команда «Хрюкерсы», кейс №2. Интерфейс на русском. Вдохновение — сайт SibКод, описание в ТЗ.
- Все интерактивные элементы имеют действие; формы валидируются; есть loading/empty/error/success. При неизвестной истории показывай unknown, не «не посещал».
- Логику объединения, сегментации и экспортных исключений получает сервер. Не создавай её параллельную реализацию в React.
- Опрос ImportJob примерно раз в 2 секунды до финального статуса; после завершения обнови зависимые query. Покупка в C должна изменить открытый профиль и сегмент после обновления данных.
- Для одного нажатия «Создать выгрузку» генерируй UUID Idempotency-Key. Сетевой повтор использует тот же UUID. «Скачать повторно» вызывает GET готового файла.
- Сохраняй decimal-строки денег; форматируй для отображения без изменения API. Даты показывай с часовым поясом.
- Пока backend не готов, допустим явный VITE_USE_MOCKS=true и мок-адаптер с ответами строго по контракту. Не смешивай моки с реальными запросами; итоговая сборка использует false.
- Выбор tenant_id/segment_id/rule_id заполняется данными API, не UUID из случайного нового набора. Seed IDs есть в manifest.

## Граница и стыковка

Твоя работа не включает исправление backend через изменение контракта. Если endpoint отсутствует, опиши точный маршрут и ожидаемый ответ для интегратора; параллельно продолжай UI на согласованном мок-адаптере. Не добавляй fallback с фиктивным успешным результатом при ошибке реального API.

Для неизвестных деталей UX принимай простые решения в пределах ТЗ. Для противоречия контракта и бизнес-смысла сформулируй одну конкретную правку для команды, не меняй общее API самостоятельно.
