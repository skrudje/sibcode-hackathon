# Хрюкерсы · Кейс №2 · Пакет для разработки

Версия 1.0 · 31 октября 2026 года.

Цель — собрать рабочую рекомендательную клиентскую платформу для ТЦ. Это внутреннее ТЗ команды для реализации на хакатоне. Оно развивает продуктовый замысел; выбранные ниже ограничения являются решениями команды для MVP, а не подтверждёнными требованиями заказчика.

## Что передавать нейронке каждого участника

1. `01_SPEC.md` — общее ТЗ. Передают все пятеро.
2. `02_OPENAPI.json` — общий HTTP-контракт. Передают все пятеро.
3. Один файл из `prompts/` — личное направление работы.
4. Папку `fixtures/` — примеры входных данных и ожидаемый демонстрационный сценарий.

Если интерфейс нейронки плохо читает JSON-вложения, сообщите ей, что это OpenAPI 3.1, и попросите прочитать файл инструментами. Не заменяйте общий контракт пересказом из памяти.

## Распределение на пять человек

| Участник | Направление | Личный промпт |
|---|---|---|
| 1 | Frontend: все экраны, интеграция API, оформление | `prompts/01_FRONTEND.md` |
| 2 | Backend-ядро: БД, миграции, авторизация, идентификация, профили | `prompts/02_CORE.md` |
| 3 | Импорт: три адаптера, проверки, фоновые задачи и восстановление | `prompts/03_INGESTION.md` |
| 4 | Сегменты, объяснимые рекомендации, оценка по актуальным событиям | `prompts/04_RECOMMENDATIONS.md` |
| 5 | Кампании, экспорт, инфраструктура, демоданные и итоговая интеграция | `prompts/05_PLATFORM.md` |

Назначьте реальные имена сами. Участник №5 отвечает за собираемость результата, но каждый участник проверяет собственный модуль и его HTTP-контракт.

## Как начать без взаимных блокировок

**Шаг 1. Общий старт.** Прочитать ТЗ; выбрать участника №2 владельцем backend-каркаса и общих моделей, №5 — владельцем интеграции. Завести один Git-репозиторий. Скопировать пакет внутрь `docs/spec/`.

**Шаг 2. Зафиксировать каркас.** №2 создаёт Python-пакет `app`, модели всех таблиц, первую миграцию, общие ошибки и точку подключения роутеров; №1 создаёт frontend-каркас и клиент по OpenAPI; №5 — Compose и пример переменных окружения. Согласовать и слить этот минимальный каркас до массовых правок общих файлов.

**Шаг 3. Параллельная реализация.** Все работают в своих ветках и каталогах. Frontend использует явно включаемые моки по контракту, пока API не готов. Backend-модули используют общие DTO и модели из каркаса, а не создают свои копии.

**Шаг 4. Сборка по вертикали.** Сначала login → источники → один импорт → профиль. Затем остальные форматы → сегмент → рекомендация → экспорт. После каждого объединения прогонять затронутые проверки.

**Шаг 5. Приёмка.** №5 запускает все сценарии раздела 13 ТЗ на собранном приложении. В конце выключить frontend-моки и проверить запуск с пустыми volumes.

## Правило разрешения противоречий

- Бизнес-смысл и ограничения определяет `01_SPEC.md`.
- Имена HTTP-полей, маршрутов, методы и схемы определяет `02_OPENAPI.json`.
- Примеры из `fixtures/` не расширяют контракт.
- При противоречии агент описывает конкретную проблему и предлагает одно согласованное исправление двух документов. Он не меняет контракт только в своей части.
- Изменения общей модели, миграций и HTTP-контракта согласуются в команде до реализации зависимых частей.

## Что должно получиться

Реальный интерфейс и работающий сервер с PostgreSQL; загрузка CRM CSV, POS XLSX и API JSON; единый профиль; динамический сегмент; объяснимая рекомендация; CSV-выгрузка; воспроизводимая демонстрация. Данные синтетические, отправка сообщений внешним адресатам не выполняется.

В комплекте нет реализации продукта. Код, конфигурацию приложения и тесты участники создают по этим документам.
